# 详细技术文档 12 · 通知服务（notification-service）

> 上游：《技术方案-后端(Java).md》v0.2 §2（服务拆分第 10 位）；PRD §3.3（流程通知）、§3.9（运营告警）
> 本文定位：实现级技术设计——消息模型、通道路由、模板引擎、站内信长连接、频控与退避
> 服务：`notification-service`；通道执行委托 `integration-service`（文档 07 预置连接器 SPI）
> 消费方：流程引擎（05：审批待办/超时催办/结果通知）、计量告警（09：用量突增）、平台运营（发布通知/安全告警）、应用自定义通知动作

---

## 1. 职责边界

| 负责 | 不负责 |
|---|---|
| 统一消息模型（通知 = 收件人 × 模板 × 通道策略） | 通道协议实现（邮件 SMTP/短信/IM 归 integration 连接器） |
| 通道路由与降级（按优先级/用户偏好选通道） | 业务触发判定（流程何时该发通知归 flow-service） |
| 模板管理与渲染（L1 表达式变量替换） | 模板可视化编辑器（前端物料职责） |
| 站内信存储、已读状态、未读数、长连接推送 | 前端通知中心 UI（文档 06FE） |
| 频控（催办 1 次/小时等）与失败退避重试 | 业务侧频控规则配置（调用方传 rateKey） |

**分工铁律**：notification 负责「发给谁、发什么、走哪条通道、失败了怎么办」；integration 负责「怎么发出去」（协议/凭证/重试）。notification 对邮件/短信通道的调用 = 对 `email.send` / `sms.send` 连接器动作的调用（文档 07 §6 SPI）。

## 2. 消息模型

```sql
CREATE TABLE notify_message (
  id            BIGSERIAL PRIMARY KEY,
  tenant_id     BIGINT NOT NULL,
  biz_type      VARCHAR(32) NOT NULL,      -- FLOW_TODO / FLOW_DONE / FLOW_URGE / QUOTA_WARN / SECURITY_ALERT / APP_NOTICE / CUSTOM
  biz_ref_id    VARCHAR(64),               -- 流程实例ID/账单ID等（跳转定位用）
  recipient_id  BIGINT NOT NULL,           -- 平台用户（站内信必有；外部通道可空改用地址）
  template_key  VARCHAR(64),               -- 系统模板或应用自定义模板
  rendered      JSONB NOT NULL,            -- {title, body, jumpUrl} 渲染结果快照
  channels      JSONB NOT NULL,            -- 实际投递通道与状态 [{channel:'INBOX', status:'DONE'}]
  status        VARCHAR(16) NOT NULL,      -- PENDING / PARTIAL / DONE / FAILED / SUPPRESSED
  occurred_at   TIMESTAMPTZ NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);          -- 按月分区，保留 12 个月

CREATE TABLE notify_user_pref (
  user_id BIGINT, tenant_id BIGINT,
  prefs   JSONB NOT NULL,                   -- {"FLOW_TODO":["INBOX","IM"],"MARKETING":[false]}
  PRIMARY KEY (tenant_id, user_id)
);
```

- `rendered` 存**渲染后快照**而非模板+变量——模板后续修改不影响历史消息展示与审计回溯；
- 外部通道失败不影响站内信（通道独立判定，见 §4 状态机）。

## 3. 模板引擎

```
模板变量上下文（L1 表达式求值，文档 08FE/01 同引擎）：
  {{ record.amount }}、{{ flowName }}、{{ approverName }}、{{ quota.metric }} ...

渲染流程：
  ① 加载模板（租户自定义 > 系统默认，缓存 5min）
  ② 变量求值（L1 受限解释器；禁止网络/文件/循环表达式——与前端 L2 同一套 AST 白名单）
  ③ 求值失败 → 该变量替换为 '--' 并标记 partial，消息照发（可用性优先）+ 告警日志
  ④ 渲染结果写入 notify_message.rendered

系统内置模板集（首版 12 个）：
  FLOW_TODO_APPROVE（待审批）/ FLOW_TODO_TIMEOUT（超时预警）/ FLOW_URGE（催办）
  FLOW_DONE_APPROVED / FLOW_DONE_REJECTED / FLOW_AGENT_ERROR（死信人工介入，05 §死信）
  QUOTA_SOFT（软限 80%）/ QUOTA_HARD（硬限拦截）/ USAGE_SPIKE（环比突增告警，09 §8）
  APP_RELEASED（应用发布）/ APP_TEMPLATE_INSTALLED / SECURITY_SENSITIVE_OP（敏感操作告警）
```

## 4. 通道路由与投递状态机

```
路由顺序（按 biz_type 声明 + 用户偏好过滤 + 通道可用性）：

  INBOX（站内信）     —— 必达通道：所有 biz_type 默认包含；写库 + 长连接推送
  IM（企微/飞书/钉钉） —— 用户绑定过三方账号才路由；委托 integration 连接器
  EMAIL              —— 用户有邮箱才路由；委托连接器
  SMS                —— 仅 SECURITY_ALERT / QUOTA_HARD 默认开；成本通道需显式启用

状态机（每通道独立）：
  PENDING → SENT（通道受理）→ DONE（回执成功）
                  ↘ RETRYING（退避重试 3 次：1m/5m/30m）→ FAILED（进死信）
  SUPPRESSED：命中频控（§5）直接标记，不投递不发

降级：IM 通道连接器不可用 → 仅保留 INBOX 通道，消息状态 PARTIAL（不阻塞业务）
```

- 站内信长连接推送：网关维护用户级 WebSocket（订阅模式），推送 `{messageId, bizType, title}` 轻载荷；前端拉详情（文档 06FE §通知中心）；连接断开兜底为未读数轮询；
- **可靠性边界**：通知是尽力而为（best-effort），审批待办以「待办列表为准」——流程引擎不依赖通知送达推进状态（05 §一致原则）。

## 5. 频控与防骚扰

```
频控键：rateKey = biz_type + ':' + recipientId（调用方可追加业务键，如流程实例）
默认窗口（Redis TTL 计数，超窗即 SUPPRESS）：
  FLOW_URGE      1 次 / 小时 / 任务（05 §催办限频）
  QUOTA_SOFT     1 次 / 天 / 指标
  USAGE_SPIKE    1 次 / 天 / 租户
  SECURITY_ALERT 不限频（安全告警宁可重复）
  CUSTOM         由调用方声明，未声明默认 10 条 / 小时 / 用户兜底
SUPPRESS 记录进 notify_message.status='SUPPRESSED'——可审计"为什么没收到"
```

- 全局护栏：单租户通知投递 QPS 上限（通道连接器侧限流，07 §护栏），超限只保 INBOX；
- 营销类（MARKETING）默认全关——用户偏好显式开启才投递（合规底线）。

## 6. 对内接口（服务端 RPC，不经网关）

```java
public interface NotificationFacade {          // 供 flow/metering/tenant 等内部调用
    void notify(NotificationCmd cmd);          // 异步：写消息 + 投递任务入队即返回
}

class NotificationCmd {
    String bizType; String bizRefId;
    Long recipientId;                          // 或 externalAddress（邮件/手机号直发场景）
    String templateKey; Map<String, Object> vars;
    List<String> forceChannels;                // 强制通道（覆盖偏好，仅系统告警用）
    String rateKeySuffix;                      // 频控键追加段（如流程实例ID）
}
```

- 异步解耦：调用方（流程动作节点）不等待投递结果；投递队列走 Kafka topic `notify.dispatch`，消费失败退避重试；
- 死信：3 次重试仍失败 → 状态 FAILED + 落死信表 + 运营告警面板可见（人工修复模板/凭证后可重投）。

## 7. 单元测试硬性要求

- [ ] 模板渲染：L1 变量求值失败的占位降级 + partial 标记；模板修改不影响历史消息
- [ ] 路由偏好：用户关闭 IM 偏好后 FLOW_TODO 只走 INBOX；MARKETING 未开启不投递
- [ ] 通道隔离：SMS 连接器故障不影响 INBOX 送达（状态 PARTIAL 判定正确）
- [ ] 频控：FLOW_URGE 一小时内第二次被 SUPPRESS 且留痕；SECURITY_ALERT 不受频控
- [ ] 异步可靠：投递任务消费失败退避 3 次后进死信；死信重投幂等（不重复推送站内信）
- [ ] 租户隔离：伪造租户上下文查询消息列表被拦截（§03 纪律）
- [ ] 长连接：断线期间的消息重连后未读数准确补齐

## 附录 A · 对外接口契约

> 前端消费方：通知中心组件与红点（前端文档 06FE §长连接）、通知偏好设置页（详细 PRD 04 §个人设置）、运营告警面板（PRD 09）。

### A.1 站内信

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/notifications?unreadOnly=&bizType=&page=&size=` | `{list:[{id, bizType, title, jumpUrl, readAt, occurredAt}], total, unreadCount}` |
| PUT | `/api/notifications/{id}/read` | 标记已读（单条） |
| PUT | `/api/notifications/read-all` | 全部已读 |
| GET | `/api/notifications/unread-count` | `{count}`（轮询兜底 + 长连接推送触发） |
| WS | `/ws/notifications` | 长连接推送 `{messageId, bizType, title}`；心跳 30s；重连带未读数快照 |

### A.2 偏好与模板

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / PUT | `/api/me/notification-prefs` | 偏好读写（`{bizType: [channels]}`；MARKETING 默认 false） |
| GET | `/api/notification/templates` | 应用可用模板清单（含系统内置 + 应用自定义，编辑器数据源） |
| POST | `/api/notification/templates` | 应用自定义模板（`{key, title, body, varsSchema}`；key 冲突 409） |
| POST | `/api/notification/templates/{key}/preview` | `{vars}` → `{title, body}` 渲染预览（编辑器实时预览） |

### A.3 错误码（本域）

| code | HTTP | 场景 |
|---|---|---|
| `TEMPLATE_NOT_FOUND` | 404 | 模板 key 不存在（含跨租户访问，同响应） |
| `TEMPLATE_KEY_EXISTS` | 409 | 自定义模板 key 与系统/既有模板冲突 |
| `NOTIFY_SUPPRESSED` | 202 | 频控命中（同步调试接口返回；异步链路仅落库标记） |

### 前端对接要点

- 通知中心消费 `/ws/notifications` 推送 + `unread-count` 轮询兜底（60s）；消息点击跳 `jumpUrl`（站内路由）；
- 偏好页读写 `notification-prefs`，MARKETING 开关独立确认弹层（合规提示）；
- 应用自定义模板编辑器：`varsSchema` 生成变量插入面板，`preview` 接口实时渲染（L1 表达式与前端同引擎，文档 08FE）。
