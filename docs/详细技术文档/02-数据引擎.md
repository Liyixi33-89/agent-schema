# 详细技术文档 02 · 数据引擎（data-engine-service）

> 上游：《技术方案-后端(Java).md》v0.2 §3/§3.1/§5；PRD §6.1（永不物理删列）
> 本文定位：实现级技术设计——存储布局、动态 SQL 构建、读时兼容、权限注入、性能
> 服务：`data-engine-service` ★平台核心服务之一

## 1. 职责边界

| 负责 | 不负责 |
|---|---|
| 业务数据物理表生命周期（建表/提升列 DDL 执行） | 字段定义元数据（归 metadata） |
| 元数据驱动的通用 CRUD/查询执行 | 页面渲染（前端） |
| 行级数据权限/字段权限 SQL 注入 | 权限定义管理（归 permission，本服务只消费） |
| 读时兼容转换、已删除字段强制过滤 | 流程编排（只被调用） |

## 2. 存储布局

### 2.1 物理表（每模型一张，建模时自动创建）

```sql
CREATE TABLE biz_model_<model_id> (
  id              BIGINT PRIMARY KEY,           -- 雪花 ID
  tenant_id       BIGINT NOT NULL,
  data            JSONB NOT NULL,               -- 全部业务字段（含已删除字段历史值）
  schema_version  INT NOT NULL,                 -- 行写入时的 Schema 版本
  created_by      BIGINT, created_at TIMESTAMPTZ,
  updated_at      TIMESTAMPTZ,
  deleted_at      TIMESTAMPTZ,                  -- 记录级逻辑删除
  -- 提升列（建模标记 indexed 后异步生成）
  status VARCHAR(50) GENERATED ALWAYS AS (data->>'status') STORED,
  amount NUMERIC GENERATED ALWAYS AS ((data->>'amount')::numeric) STORED
);
CREATE INDEX idx_<model_id>_tenant ON biz_model_<model_id>(tenant_id, deleted_at);
CREATE INDEX idx_<model_id>_gin ON biz_model_<model_id> USING GIN(data);
-- 提升列各建单列/组合索引
```

### 2.2 表数量控制策略

| 模式 | 触发条件 | 说明 |
|---|---|---|
| 独立表（默认） | 租户模型数 ≤ 200 | 查询性能最优 |
| 共享表 | 超上限或平台判定 | `biz_data_unified(model_id, tenant_id, data...)` + 按 model_id 的 partial index |

### 2.3 关联存储

| 关系 | 存储 | 查询 |
|---|---|---|
| 1:1 / 1:n | JSONB 内存对方记录 id（高频提升列） | DataLoader 批量二次查询 + 内存拼装，杜绝 N+1 |
| n:n | 中间表 `rel_<a>_<b>(a_id, b_id, tenant_id)`，双列复合索引 | 批量 IN 查询 |

### 2.4 与 PRD §6.1 对齐的存储规则

| 变更 | 行为 |
|---|---|
| 新增字段 | 无 DDL；旧行 data 无该键 → 读取按默认值/null 填充 |
| 改类型 | **协议禁止**（field_type 创建后不可变，见 01BE §3 MODIFAY 白名单）；换类型 = 新建字段，存量数据由用户用数据体检工具（PRD 01 §2.9）迁移。本引擎只需处理「新增字段的旧行无键」与「读时版本比对」两类兼容 |
| 删字段 | 无 DDL；data 键与提升列**永不移除** |
| 提升列 | 唯一触发 DDL 的操作：`ADD COLUMN ... GENERATED ALWAYS AS ... STORED` + 索引，异步任务执行 |
| 删提升列 | **不 DROP COLUMN**，仅元数据停止引用 |

## 3. 动态查询引擎

### 3.1 接口

```java
public interface DynamicQueryEngine {
    PageResult<Map<String, Object>> query(QueryRequest req);
    Map<String, Object> getById(String modelId, Long id);
    Long create(String modelId, Map<String, Object> data);
    void update(String modelId, Long id, Map<String, Object> data);
    void delete(String modelId, Long id);           // 逻辑删除：写 deleted_at
    BatchResult batchUpsert(String modelId, List<Map<String,Object>> rows, String keyField);
    AggregateResult aggregate(AggregateRequest req); // 仪表盘聚合查询（§3.6）
}

class QueryRequest {
    String modelId;
    ConditionTree filter;        // AND/OR 嵌套树
    List<Sort> sorts;            // Sort{field: String, order: 'asc'|'desc'}；field 须 ACTIVE 且过元数据白名单（§3.3 第 5 步同口径）
    int page, size;              // size 硬上限 200
    List<String> fields;         // 投影
    int relationDepth;           // 关联级联深度，默认 1，上限 2
    boolean includeDeletedFields; // 仅管理员，记审计
}
```

### 3.2 过滤条件树协议

```json
{ "op": "AND", "conds": [
    { "field": "status", "op": "eq", "value": "approved" },
    { "field": "amount", "op": "between", "value": [1000, 50000] },
    { "op": "OR", "conds": [ { "field": "dept", "op": "in", "value": ["d1","d2"] } ] }
] }
```

操作符白名单：`eq / ne / in / nin / like / between / gt / gte / lt / lte / isnull`。**不在白名单 = 直接 400**。

### 3.3 SQL 构建流程（核心算法）

```
buildQuery(req):
  1. 加载元数据（Caffeine→Redis→DB 三级缓存，带 version 比对）
  2. 校验：模型 ACTIVE；每个 filter.field 存在且 field_status='ACTIVE'
     （DELETED 字段 400，不给数据线索；includeDeletedFields 白名单走管理员审计通道）
  3. 字段→物理表达式映射：
     promoted & promote_status='ACTIVE'  → 直接用列名  status = ?
     否则                                 → (data->>'amount')::numeric ?（按字段类型 cast）
  4. 注入固定条件（顺序不可变）：
     WHERE tenant_id = :ctx.tenantId         ← 租户拦截器兜底（双保险）
       AND deleted_at IS NULL                ← 记录逻辑删除过滤
       AND <行级数据权限条件>                 ← permission-service 注入（§03）
  5. 字段投影：SELECT data || jsonb_build_object('_id', id) 或按投影提取；
     字段权限剔除：不可见字段从 SELECT 与响应中移除（列级）
  6. 值一律 PreparedStatement 占位符；字段名/操作符仅来自元数据白名单——杜绝拼接
  7. LIMIT :size（≤200）；深分页 page*size > 100000 时返回 400 + 提示走 cursor
```

### 3.6 聚合查询（仪表盘数据源，P2）

> 前置契约：前端 `useModelAggregate(modelId, agg)`（前端文档 07 §3）；PRD 02 §2.6「模型聚合（分组/计数/求和）」。**明确不做自由 BI：无自定义 SQL、无跨模型 join 聚合**（PRD 02 §2.6 红线）。

```java
class AggregateRequest {
    String modelId;
    ConditionTree filter;              // 与查询共用同一过滤树协议（§3.2 白名单）
    List<AggMeasure> measures;         // 度量，1-5 个
    AggGroup group;                    // 分组维度，可选（无分组 = 全表单值）
    AggTimeBucket timeBucket;          // 时间分桶，可选
}

class AggMeasure {
    String fieldKey;                   // 计数字段固定为 "__count"（伪字段）
    AggFunc func;                      // SUM / AVG / COUNT / COUNT_DISTINCT / MAX / MIN
}

class AggGroup {
    String fieldKey;                   // 分组字段（文本/枚举/日期）
    int topN;                          // 取前 N 组，默认 10，上限 50
}

class AggTimeBucket {
    String fieldKey;                   // 日期类型字段
    String interval;                   // DAY / WEEK / MONTH
}
```

**SQL 构建规则（复用 §3.3 管线，插入聚合段）**：

```
buildAggregate(req):
  1-2. 元数据校验与固定条件注入：与 query() 完全一致
     （租户、deleted_at、行级权限、字段 ACTIVE 校验——聚合结果同样受行级权限约束，
       权限外记录对聚合值不可见，防止"看不到明细但统计含沙数"）
  3. 维度表达式：
     文本/枚举分组      → data->>'dept'（或提升列）
     时间分桶 DAY       → date_trunc('day', (data->>'created_at')::timestamptz)
     时间分桶 WEEK/MONTH→ date_trunc('week'|'month', ...)（周起点取 ISO 周一）
  4. 度量表达式：
     SUM/AVG   → ((data->>'amount')::numeric)
     COUNT     → COUNT(*)
     COUNT_DISTINCT → COUNT(DISTINCT data->>'owner')
     MAX/MIN   → max/min((data->>'price')::numeric)
  5. GROUP BY 维度表达式（别名 dimension）+ ORDER BY 度量 DESC
     → 子查询 LIMIT :topN 后整体包装（保证 topN 截断后再算总计行）
  6. 响应：{ rows:[{dimension, values:[{func, fieldKey, value}]}],
            total?（无分组单度量时的快捷单值） }
  7. 防护栏：单聚合 SQL 复用 statement_timeout 3s 熔断；
     时间分桶跨度过大（区间桶数 > 1000）返回 400 引导缩小范围
```

- **性能**：分组/度量字段未建提升列时聚合走 JSONB 表达式全表扫——响应头 `X-Suggest-Index` 同 §6 引导设提升列；仪表盘卡片高频查询建议前端 staleTime ≥ 60s（前端文档 07 hooks 约定）。
- **口径一致性**：聚合结果与列表查询走同一权限注入管线——不做独立聚合表/预计算（P2 范围内数据量级下实时聚合足够；若后续千万级聚合卡顿，再评估物化视图，届时另行决策记录）。

```
create/update(modelId, data):
  1. 元数据校验：字段存在/ACTIVE/类型匹配（Jackson 反序列化 + 校验器链：
     required→长度/正则→范围→唯一→自定义表达式(Aviator 受限求值)）
  2. 计算字段（PERSISTED）：执行表达式重算后写入；READ_TIME 类型剔除写键
  3. relation 字段：目标记录存在性校验（批量查目标表）
  4. JSON 序列化 data + schema_version=currentVersion 落库
  5. 唯一约束：唯一字段靠「提升列 + UNIQUE 部分索引」保证（无提升列的唯一校验为应用层先查后写 + 说明并发风险）
  6. 事务提交后：发领域事件 record.created/updated/deleted 到 MQ
     （流程触发器、Webhook、计量都消费此事件）
```

### 3.5 读时兼容（对应"不做迁移"决策）

```
readRow(row, schema):
  for each field in schema.ACTIVE fields:
    raw = row.data[field.key]
    if raw == null → 填 default 或 null
    else 按字段类型宽松解析：
      解析成功 → 强类型值
      解析失败 → 保留原始值 + 标记 _invalid:[fieldKey]
                （前端展示 '--'，数据体检工具可扫描此标记）
  只读转换，永不回写数据库
```

版本比对优化：`row.schema_version == currentVersion` 时跳过兼容层直出（热路径零开销）。

## 4. 提升列 DDL 执行器

```
消费 MQ topic: ddl.promote
任务状态机：PENDING → BUILDING → ACTIVE / FAILED
  BUILDING: ALTER TABLE biz_model_x ADD COLUMN ... GENERATED ... STORED
            （PostgreSQL 11+ STORED 列为元数据级操作，秒级，不重写全表——这是选 STORED 而非 VIRTUAL 的原因之一是兼容版本，之二是索引必须建在 STORED 上）
            + CREATE INDEX CONCURRENTLY（不锁写）
  失败：promote_status='FAILED'，任务可重试；期间查询自动回退 JSONB 表达式
幂等：任务表唯一键 (model_id, field_key)；重复消费直接 ACK
```

## 5. 与调用方的权限一致性

| 调用方 | 权限传递 |
|---|---|
| 页面 request-sdk | 用户 JWT → 功能权限校验（网关）→ 行级/字段注入（本服务） |
| 开放 API（API Key） | Key 授权范围（模型×动作）+ 可配数据范围规则 + 绑定角色的字段权限 |
| 流程动作节点 | 流程发起人上下文透传（内部 RPC 携带） |
| L3 脚本 | ExecContext 透传（租户+用户+角色），SQL 层二次校验——不信任脚本层 |

**统一铁律：所有读写必经 DynamicQueryEngine，直连表访问在业务代码中禁止（CI 规约扫描）。**

## 6. 性能设计

| 措施 | 说明 |
|---|---|
| 深分页防护 | size≤200 硬限；page*size>10 万拒绝引导 cursor（keyset：`WHERE id > :lastId ORDER BY id LIMIT :size`） |
| 慢查询熔断 | 单查询执行计划超时（`statement_timeout` 按 3s）→ 熔断提示 + 慢查询日志（含 EXPLAIN 摘要） |
| 索引引导 | 未建索引字段过滤 + 行数>50 万 → 响应头 `X-Suggest-Index` 引导设提升列 |
| 大表治理 | 千万级行引导归档（deleted_at 分区）或原生分区表 |
| 批量写 | batch-upsert 走 COPY/unroll batch，单批 ≤ 500 行 |
| DataLoader | relation 批量拼装，单请求内合并去重（防 N+1） |
| 无状态 | 服务无本地磁盘依赖，按租户分片路由可水平扩展 |

## 7. 批量导入导出（P2）

- 导入：上传 → 异步解析（行流式读取）→ 预校验任务（错误行报告文件）→ 用户确认后走 batch-upsert；全程任务表可查进度。
- 导出：筛选条件 → 异步游标扫描流式写 Excel（SAX 写，防 OOM）→ 对象存储 → 下载中心；**导出前字段权限二次过滤 + 全量审计**；上限 10 万行。

## 8. 单元测试硬性要求

- [ ] SQL 注入：字段名/操作符/值三维度注入样本全部被拦截
- [ ] 已删除字段：任何参数组合（含伪造 fields 投影）不可读出 DELETED 字段
- [ ] 读时兼容：旧版本行的类型不匹配值标记 `_invalid` 而非抛错
- [ ] 租户过滤：伪造上下文被拦截（配合 §03 越权用例）
- [ ] 提升列：任务失败后查询回退 JSONB 表达式不报错
- [ ] DataLoader：100 行含 relation 的列表页查询只产生 2 条 SQL（主查 + 批量关联）
- [ ] 聚合权限：行级权限外记录不参与 SUM/COUNT（构造 100 行、权限可见 60 行，聚合值=60 行口径）
- [ ] 聚合分组：时间分桶 WEEK 按 ISO 周一起算；topN 截断后总计行不受影响
- [ ] 聚合护栏：桶数 >1000 返回 400；聚合 SQL 超时熔断返回统一错误码

## 附录 A · 对外接口契约（统一 CRUD 协议）

> 前端消费方：request-sdk 通用 hooks（前端文档 07 §3）、列表/表单页数据源（文档 02FE §2 管线）、运行时 ActionDispatcher（文档 02FE）。
> 响应体：分页统一 `{list, total, page, size}`；字段级权限已在响应中物理剔除（文档 03 §3——前端只做「键缺失」容错，不做二次过滤）。

### A.1 记录 CRUD

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/api/data/{modelId}?filter=&sort=&page=&size=&fields=&relationDepth=&includeDeletedFields=` | query 参数见 A.2 | `{list:[Record], total, page, size}` |
| GET | `/api/data/{modelId}/{id}` | — | `Record`（`{_id, ...字段}`, 键已按字段权限剔除） |
| POST | `/api/data/{modelId}` | `Record`（全量表单提交；不可编辑字段服务端静默忽略） | `{id}` 201 |
| PUT | `/api/data/{modelId}/{id}` | `Record` | `{}` 200 |
| DELETE | `/api/data/{modelId}/{id}` | — | `{}` 200（逻辑删除） |
| POST | `/api/data/{modelId}/batch` | `{rows:[Record], keyField}` | `{inserted, updated, failed:[{index, reason}]}` |

`Record = Record<string, JsonValue>`；`_id` 为平台注入主键，写入时忽略。

### A.2 查询参数协议（与 §3.1 QueryRequest 一一对应）

| 参数 | 类型 | 约束 |
|---|---|---|
| `filter` | ConditionTree JSON（§3.2） | 操作符白名单：eq/ne/in/nin/like/between/gt/gte/lt/lte/isnull；越界 400 |
| `sort` | `[{field, order}]` | 字段须 ACTIVE |
| `page` / `size` | int | **size ≤ 200**（前端 hook 层 clamp，前端文档 07 §3）；page×size > 100000 → 400 引导筛选 |
| `fields` | `string[]` 投影 | DELETED 字段 400 |
| `relationDepth` | int 0-2 | 默认 1 |
| `includeDeletedFields` | bool | 仅管理员，每次调用记审计 |

### A.3 唯一性校验（表单异步校验）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/data/{modelId}/unique-check` | `{fieldKey, value, excludeId?}` | `{unique: boolean}`（排除自身记录，编辑场景必传 excludeId） |

### A.4 聚合查询（仪表盘数据源）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/data/{modelId}/aggregate` | `AggregateRequest`（§3.6：`{filter, measures:[{fieldKey, func}], group?:{fieldKey, topN}, timeBucket?:{fieldKey, interval}}`） | `{rows:[{dimension, values:[{func, fieldKey, value}]}]}`（无分组时 `rows` 单行、dimension=null） |

- POST 而非 GET：聚合参数结构复杂（过滤树 + 度量数组），query 参数放不下，且聚合只读可缓存无幂等副作用问题；
- `useModelAggregate(modelId, agg)`（前端文档 07 §3）直连此接口，queryKey 含完整 agg 结构；
- 响应头 `X-Suggest-Index`：聚合字段未提升时的引导（同 A.1 列表查询）。

### A.5 导入导出（P2）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/data/{modelId}/export` | `{filter, fields}` | `{taskId}`（异步任务，下载中心轮询） |
| POST | `/api/data/{modelId}/import` | multipart 文件 | `{taskId, precheckUrl}` |

### A.6 错误码（本域）

| code | HTTP | 场景 |
|---|---|---|
| `FILTER_OPERATOR_INVALID` | 400 | 非白名单操作符 |
| `FIELD_DELETED` | 400 | filter/fields 引用 DELETED 字段 |
| `PAGE_TOO_DEEP` | 400 | 深分页超限 |
| `RECORD_NOT_FOUND` | 404 | 详情/更新目标不存在（或行级权限不可见，同响应不给线索） |
| `VALIDATION_FAILED` | 422 | 写入违反字段校验规则（`{fieldKey: message}` 附表） |

### 前端对接要点

- `useModelList/useModelDetail/useSaveModel` 封装见前端文档 07 §3（queryKey 结构化，mutation 成功失效 `['model', modelId]`）；
- ConditionTree 与前端 `FilterNode` 的序列化映射由 `encodeQuery` 承担（前端文档 07 §3），契约测试锁定；
- `_invalid` 标记值（读时兼容）：前端渲染为「数据异常」占位而非报错（前端文档 02FE §8 分级）。
