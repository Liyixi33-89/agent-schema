## 1. 为什么是 DDD

平台的领域复杂度不在算法，而在「**一个 Schema 定义同时被建模、渲染、流程、权限、计量五个视角消费**」。贫血 CRUD + 服务大杂烩会让"字段删除"这类核心规则散落在十个 Service 里互相打架（后端文档 01 的字段状态机就是教训预防针）。DDD 的价值正是把这类**不变式收进聚合根**，把跨域规则变成**上下文间的显式契约**，支撑「模块化单体 → 服务拆分」的既定演进路线（技术方案 §1）。

```
│  ┌───────────────┐  ┌──────────────┐  ┌─────────────────────┐  │
│  │ 元数据上下文    │  │ 页面上下文     │  │ 流程上下文            │  │
│  │ metadata       │  │ page/build    │  │ flow（Transpiler+   │  │

│  └───────────────┘  └──────────────┘  │ (文档05)             │  │

│  │ gateway (06) │ │ sandbox (08)│ │ infra (10) file(11)      │  │
│  │              │ │             │ │ notify(12)  ai-gw(14,P3) │  │

```

**上下文判定纪律**：按「语言边界」划，不按技术分层划。判据——同一个词在两个上下文里有不同含义才拆。例：`字段`在元数据上下文是 FieldSchema（含状态机），在数据上下文只是 JSONB 的一个 key，在页面上下文是可绑定引用——三个上下文必须各自建模，禁止共享实体类。

### 2.2 上下文映射（集成关系全部显式化）

| 上游 → 下游 | 关系模式 | 集成方式 | 防腐层位置 |
|---|---|---|---|
| 页面 → 元数据 | **客户-供应商**（页面引用字段，元数据定规则） | 同步 API（引用登记）+ 异步广播（缓存失效） | page-service 内 `FieldRefAdapter` |
| 流程 → 数据引擎 | **客户-供应商** | 内部 RPC（动作节点写数据） | flow 的 `DataCommandAdapter`（继承调用者权限的透传在此收口） |
| 流程 → 权限 | **客户-供应商**（动态审批人监听回调） | 同步查询 | permission-client |
| 集成/L4 → 外部服务 | **防腐层**（客户自有 HTTP 是外部系统） | 连接器管线（SSRF 六步，文档 07） | Connector 本身就是 ACL |
| L3 沙箱 → 数据引擎 | **防腐层**（客户代码是最不可信的外部系统） | 序列化边界 + 封装接口（文档 08） | ScriptDataGateway |
| 元数据 → 数据引擎 | **发布-订阅**（DDL 提升任务） | MQ topic `ddl.promote` | DDL 执行器消费 |
| 全部 → 计量 | **发布-订阅**（事件单向流） | MQ topic `metering.raw` | 无（事件模型即契约，文档 09） |
| 网关 → 全部 | **开放主机服务**（OHS） | 统一 REST 协议 + 动态 OpenAPI | 网关本身就是 OHS 的实现 |

**映射纪律**：
- 上游上下文**不感知**下游存在（元数据不知道页面怎么用字段——影响面分析靠页面反向登记引用）；
- 跨上下文调用**禁止共享数据库表**（模块化单体阶段禁跨模块 join，为拆分保留切口——文档 10 §模块边界）；
- 「跟随者」关系明确标注：Flowable/MinIO/Kafka 是被跟随的成熟方案，平台侧只做适配器（文档 10 外部依赖接口化红线）。

## 3. 分层架构（每个上下文内部统一）

```
模块内四层（模块化单体，Maven 多 module；未来按上下文直接切出为服务）

┌──────────────────────────────────────────────────────┐
│ interfaces 接口层                                     │
│   REST controller / MQ listener / 定时任务入口          │
│   职责：协议转换（DTO↔命令）、租户上下文装配、鉴权注解      │
│   禁止：业务逻辑、直接调用 repository                   │
├──────────────────────────────────────────────────────┤
│ application 应用层                                    │
│   用例服务（XxxCommandService / XxxQueryService）      │
│   职责：编排领域对象、事务边界、跨上下文协调、事件发布       │
│   禁止：业务规则判断（下沉领域层）、SQL                   │
├──────────────────────────────────────────────────────┤
│ domain 领域层 ★唯一封装业务规则的地方                   │
│   聚合根 / 实体 / 值对象 / 领域服务 / 领域事件 / 仓储接口   │
│   职责：不变式守卫（如字段状态机）、纯业务规则             │
│   禁止：框架依赖（Spring 注解只允许在 factory/config）    │
├──────────────────────────────────────────────────────┤
│ infrastructure 基础设施层                              │
│   仓储实现（JPA/MyBatis）/ 外部适配器 / 缓存 / MQ 封装    │
│   职责：技术细节实现领域层定义的接口（依赖倒置）           │
└──────────────────────────────────────────────────────┘

依赖方向：interfaces → application → domain ← infrastructure
（infrastructure 实现 domain 定义的仓储/网关接口——DIP 是 DDD 可测试性的根基）
```

### 3.1 模块（Maven module）与上下文的映射

```
schema-platform/                        （模块化单体）
├── platform-common/                    （值对象/工具，无业务）
├── metadata-module/                    （上下文=模块，四层各自成 package：
│   ├── command-api / query-api         interfaces 层对外契约，供其他模块编译依赖）
│   ├── application/
│   ├── domain/
│   └── infrastructure/
├── data-module/  page-module/  flow-module/
├── iam-module/  integration-module/  metering-module/
├── file-module/  notify-module/  tenant-module/     （文档 11/12/13——通用域+支撑域）
├── sandbox-executor/                   （独立部署物——L3 物理隔离铁律，文档 08）
└── bootstrap/                          （组合根：Spring Boot 启动 + 模块装配）
```

**模块纪律（CI 强制，ArchUnit）**：
- 模块间只依赖对方 `*-api`（interfaces 层契约包），碰 `domain/infrastructure` 编译失败；
- 每个 `*-api` 的公共方法必须有对应鉴权语义注释与契约测试（开放主机服务的最小单元）。

## 4. 战术设计模式（模式 → 落点 → 解决什么）

> 与前端总纲同理：只在解决已识别问题时引入，每条对应现有文档的具体章节。

### 4.1 元数据上下文（文档 01）

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **聚合根** | `ModelAggregate`（Model + Fields + Relations 一致性边界） | 字段状态机/唯一性等不变式收口：删除字段必经聚合根 `deleteField()`，内联影响面确认标记与版本递增，Service 层无法绕过 |
| **值对象** | `FieldKey` `FieldType` `PromoteStatus`（无 setter，相等按值） | field_key 命名规则、类型白名单的验证在构造时完成，脏数据无法诞生 |
| **领域事件** | `SchemaVersionCreated` `FieldDeleted`（事务提交后发布） | 缓存失效广播、DDL 任务投递、计量事件全部解耦于保存用例（文档 01 §4 事务流程的"事务提交后"三件事） |
| **快照 + 事件溯源（轻量）** | `meta_schema_version`（snapshot + diff） | 回滚=加载快照走正向流程（文档 01 §4.4）；不引入完整 ES，快照表够用 |
| **规格模式** | `HighRiskChangeSpec`（confirmMode 判定） | TYPE_MODEL_NAME/CHECKBOX/INFO 分级规则可组合、可单测（文档 01 §4.3） |
| **乐观并发** | `current_version` 比对 | 并发保存冲突显式化（409 而非互相覆盖） |

### 4.2 数据上下文（文档 02）

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **解释器** | `QueryRequest` 过滤树 → 动态 SQL 构建器 | 统一查询协议（后端 §5）的执行核心；白名单校验在此强制（字段名/操作符来自元数据） |
| **管道模式** | 查询执行管线：租户注入→行权限→字段过滤→类型转换→分页 | 每段独立可测；权限注入的强制性靠管线顺序保证（文档 03 的 SQL 注入层） |
| **策略模式** | 读时兼容策略（DELETED 字段剔除/类型降级/提升列回退） | 字段变更后存量数据无感读取（PRD §6.1 读时兼容决策） |
| **工厂** | `RowMapper`（按元数据字段集动态组装结果对象） | 动态模型没有静态实体类，行映射纯元数据驱动 |

### 4.3 页面/流程上下文（文档 04/05）

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **状态模式** | 页面草稿/发布态（draft/published 分离） | 保存即编译、发布即快照——状态即存储布局（文档 04 §1.2） |
| **防腐层** | `FlowTranspiler`（自定义 Schema→BPMN XML） | 不让 Flowable 的概念渗入领域模型（后端 §6 核心决策：复用引擎不重复造轮子，但隔离其 API） |
| **适配器 + 监听器** | 动态审批人 `TaskListener` 回调 permission | 审批人规则运行时解析，建模时不写死（后端 §6） |
| **幂等动作** | 动作节点执行（幂等键 + 死信队列） | 流程动作重试不重复执行（文档 05） |
| **建造者** | `AppReleaseSnapshotBuilder`（发布聚合页面/模型引用/产物 hash） | 发布快照的组装复杂度收口（文档 04 §1.3） |

### 4.4 平台横切上下文（文档 03/06/07/08/09）

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **装饰器（拦截器链）** | 网关过滤器链：租户→鉴权→限流→配额→审计（文档 06） | 横切关注点顺序强制、可插拔 |
| **模板方法** | SSRF 六步管线（解析→白名单→IP 校验→重定向检查→代理调用→日志，文档 07） | 安全检查步骤不可跳过、新增检查只加步骤 |
| **外观** | `ScriptDataGateway`（沙箱只见封装接口，文档 08） | L3 数据访问必须继承调用者权限的最小暴露面 |
| **管道** | 计量事件链路（校验→去重→归一→聚合，文档 09） | 幂等与时间归属规则集中可见 |
| **规格模式** | 配额判定（软限/硬限/宽限期） | 档位规则演进不改扣减主流程（文档 09 §6） |

### 4.5 仓储与事务

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **仓储** | 每 agg根一个 Repository 接口（domain 层定义，infrastructure 实现） | 聚合边界外的对象无法被持久化路径触达 |
| **工作单元** | Spring `@Transactional` 边界 = 聚合保存边界 | 事务只包一个聚合的修改；跨聚合最终一致（领域事件 + MQ） |
| **Outbox 模式** | 领域事件发布（本地表 + 投递器，文档 10 缓存一致性） | 事务提交与事件发布的原子性（广播丢失=缓存脏读事故） |

## 5. CQRS 轻量化（查询不走聚合根）

平台查询远重于命令（列表/筛选/聚合/导出），全走聚合根加载会把大字段 JSONB 拖进内存。纪律：

- **命令侧**：Controller → CommandService → 聚合根（完整不变式校验）→ 仓储保存 → 领域事件；
- **查询侧**：Controller → QueryService → 直接 SQL/投影 DTO（不过聚合，但**必须走数据上下文的权限注入管线**——查询简化不能绕开行/字段级权限，这是红线）；
- 两侧共享同一仓储的元数据缓存（文档 01 §5），读写模型由同一 Schema 定义驱动，无独立读库（P3 前）。

## 6. 演进路线：模块化单体 → 微服务（DDD 买到的期权）

| 阶段 | 形态 | 触发条件 | DDD 提供的切口 |
|---|---|---|---|
| P1-P2 | 模块化单体（单 bootstrap，多 Maven module） | 默认 | 模块=限界上下文，api 包=未来 RPC 契约 |
| P2+ | sandbox-executor 独立部署 | 已定（L3 物理隔离铁律） | 上下文边界即部署边界 |
| P3 | 高压上下文切出（如 data-engine、metering） | 单上下文资源画像显著异质（文档 10 演进判据） | 切出时 api 包加 RPC 适配器即可，领域层零改动 |

**拆分前置检查（现在就守）**：禁跨模块表 join；跨模块只走 api 包；每模块独立 Flyway 脚本目录（文档 10 CI 硬性项）。

## 7. 反模式清单（明确禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 贫血模型（Entity 全 getter/setter，规则在 Service） | 字段状态机会被十处调用点绕过；不变式必须封装在聚合根 |
| 跨模块共享 JPA 实体 | 拆分切口立即失效；上下文语言互相污染 |
| Service 层互相调用形成网 | 编排属于 application 层单点（跨上下文编排放最上层用例或事件） |
| 用 DTO 当领域对象层层传递 | DTO 属 interfaces 层，进 domain 必转换 |
| 在领域层写 SQL/调中间件 | 可测试性归零；依赖倒置被架空 |
| 一个事务改多个聚合 | 改用领域事件 + 最终一致；跨聚合同步事务=拆分时的分布式事务噩梦 |
