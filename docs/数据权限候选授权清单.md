## 一、核心问题：`app_id=1` 从不存在

| 事实 | 数据 |
|---|---|
| `app` 表 id 范围 | **235 ~ 264**（共 29 条） |
| `app` 表有 `id=1` 的记录吗 | **没有**（含软删） |
| `app_id_seq` 当前值 | 264 |
| `app` 表最早记录 | 2026-11-26 16:57:41 |
| 最早孤儿模型（`app_id=1`） | 2026-11-26 17:05:07（**晚于 app 最早记录 8 分钟**） |

**结论**：`app_id=1` 是一个**从未存在过的 app id**，不是「被删除的应用」。
模型在 11-26 17:05 起被写入该 id——与 IT 测试运行时间吻合。

**根因**：`meta_model` / `page_schema` **都没有 `app_id` / `model_id` 外键约束**，
写入时不做存在性校验，因此可以自由写入任意 app_id。

## 六、下一步：一致性问题（不通过授权掩盖）

需要先解决「模型/页面/发布记录指向不存在的应用」，否则授权只是把问题藏起来。

待你决定的处置方向：

**A. 清理孤儿数据**（推荐先做）
- 删除 `app_id=1` 的 64 个模型 + 30 个页面 + 48 条发布记录
- 前提：确认这些全是测试产物（当前证据支持，但需你确认无人工创建的业务模型）

**B. 恢复应用关联**
- 建一个真实应用，把需要的模型迁移过去
- 前提：确认哪些模型是真正需要的（目前看不出任何真实业务模型）

**C. 补外键约束防再发**
- `meta_model.app_id` 与 `page_schema.model_id` 加外键（或应用层存在性校验）
- 这会阻止未来写入孤儿数据，但历史数据仍需单独处置

**我的判断**：先做 A（清残留）+ C（加约束防再发），再做 B（真实试点）。
但 A 涉及删除，需要你明确批准；C 涉及迁移脚本与协议变更，也需要你确认。

## 七、授权配置模板（等确定模型后再执行）

按你的要求：**专用角色、事务内变更、保留回滚记录**。

```sql
-- 1) 备份现有授权（回滚依据）
CREATE TABLE IF NOT EXISTS _bak_role_data_scope_20261127 AS
SELECT * FROM sys_role_data_scope;

-- 2) 事务内建专用角色并按模型授权（示例：仅报销试点）
BEGIN;
-- 2.1 专用角色（不与 app_admin/platform_admin 等共享角色混用）
INSERT INTO sys_role (tenant_id, code, name, role_type)
VALUES (1, 'biz_data_manager', '业务数据管理员', 'TENANT')
ON CONFLICT DO NOTHING;

-- 2.2 按确认的模型授权（model_id 需替换为实际值）
INSERT INTO sys_role_data_scope (role_id, model_id, scope_type, scope_expr)
SELECT r.id, :model_id, 'ALL', NULL
FROM sys_role r WHERE r.code='biz_data_manager' AND r.tenant_id=1
ON CONFLICT DO NOTHING;

-- 2.3 关联到指定账号（仅目标账号，不影响他人）
INSERT INTO sys_user_role (user_id, role_id)
SELECT u.id, r.id FROM sys_user u, sys_role r
WHERE u.account=:account AND r.code='biz_data_manager' AND r.tenant_id=1
ON CONFLICT DO NOTHING;
COMMIT;
```
