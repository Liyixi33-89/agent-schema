## 1. 部署拓扑与权限模型

### 1.1 进程与端口

| 组件 | 形态 | 端口 | 说明 |
|---|---|---|---|
| Spring Boot（`schema-platform.jar`） | systemd 服务 `schema-platform` | 18080（仅本机回环） | `ExecStart -jar /opt/schema/current/schema-platform.jar`；版本经 `EnvironmentFile=-/etc/schema-release.env`（`APP_VERSION`/`GIT_COMMIT`）注入探针 |
| Nginx | systemd 服务 | 80（公网） | 静态根 `/opt/schema/current/web`；`/api/` 反代 18080；三个 SPA 入口 `/`、`/designer/`、`/admin/` |
| PostgreSQL | 本机实例 | 5432（默认仅本机） | 库 `schema_prod`；迁移由 Flyway 在应用启动时执行 |

### 1.2 目录布局

```
/opt/schema/
├── releases/<commit>/           # 版本目录（不可覆盖、不可修改）
│   ├── schema-platform.jar
│   ├── web/{runtime,designer,admin}
│   ├── VERSION.txt              # commit / builtAt / jarSha256
│   ├── MANIFEST.sha256          # 全量文件哈希清单（上传闸门）
│   └── dbBaseline               # 该版本携带的最高 Flyway 迁移号（回滚边界判定）
├── current -> releases/<commit> # 当前运行版本（软链）
├── release-state.json           # {current, previous, switchedAt}（原子写）
├── staging/                     # 上传暂存（校验通过才 mv 入库）
├── backups/                     # DB + 文件备份（700/600）
├── data/files/                  # 运行时上传文件（文件服务存储根）
├── schema-release.sh / schema-backup.sh / restore-verify.sh
└── /etc/schema-release.env      # 版本注入（600, root）
```

### 1.3 账号与权限边界

| 账号 | 用途 | 权限 |
|---|---|---|
| `root` | 初始化/救援 | 全量 |
| `deploy` | 日常发布通道 | sudo 白名单 `NOPASSWD` 仅三支脚本：`schema-release.sh *`、`schema-backup.sh`、`restore-verify.sh`；脚本本体 root 属主 750，deploy 不可篡改 |

- sudo 白名单由 `scripts/setup-deploy-user.sh` 安装（`/etc/sudoers.d/schema-deploy`，440）；
- 三支脚本内部自有闸门（发布锁/MANIFEST/迁移边界），故参数不设限；
- deploy 拿不到三支脚本之外的任何 root 权限——泄露 deploy 私钥的影响面收敛在「发布/回滚/备份」操作内。

## 2. 产物协议

| 文件 | 生成方 | 作用 | 验证方式 |
|---|---|---|---|
| 版本号（commit） | `deploy.py require_clean_head` | 只能发布当前检出的干净 HEAD——线上版本可精确追溯到唯一 commit | 发布前本地校验；发布后与探针 `commit` 字段比对 |
| `VERSION.txt` | `deploy.py make_version_file` | `commit=`、`builtAt=`、`jarSha256=` | 人工核对：`cat /opt/schema/current/VERSION.txt` |
| `MANIFEST.sha256` | `deploy.py make_manifest` | jar + web 全量文件 sha256 清单（格式与 `sha256sum -c` 兼容） | 服务器 `upload` 阶段逐条比对，任一不符拒绝入库 |
| `dbBaseline` | 服务器 `upload` 从 jar 内 `db/migration/V*` 提取 | 该版本要求的最高迁移水位 | `rollback` 时与库实际水位比对（§5.2） |

**不变量**：`releases/<commit>` 一经入库不可覆盖、不可修改；同 commit 重复上传直接拒绝（`版本已存在`）。

## 3. 发布流程

### 3.1 本地/CI 发布（推荐路径）

```
python scripts/deploy.py --version <commit>
```

步骤（一条链，任一步失败即中止）：

1. **版本校验**：工作区干净 + HEAD == 目标版本（`require_clean_head`）；
2. **verify**：`verify.ps1 -Level commit`（七步：文档/前端 tsc/后端编译/契约 diff/前端 build/前端测试/后端测试；CI 已跑可 `--skip-verify`）；
3. **构建**：后端 jar（`mvn -pl bootstrap -am package`）+ 三前端 dist（`pnpm build`）；
4. **打包**：`VERSION.txt` + `MANIFEST.sha256` 随产物入 tar；
5. **上传**：tar 流经 SSH 到 `schema-release.sh upload <commit>`——MANIFEST 逐条校验通过才入库（§2）；
6. **切换**：`schema-release.sh switch <commit>`（服务器侧：发布锁 → 发布前 DB 备份 → 切链 → 重启 → 全量验证 → 失败自动回滚，见 §3.2）；
7. **发布后独立复验**（不信任服务器脚本自身结论）：三入口 HTTP 200 + 探针 commit == 目标；任一不符自动触发服务器侧回滚。

### 3.2 服务器侧切换闸门（`switch` 子命令）

```
acquire_lock（flock /run/lock/schema-release.lock——手工与 CI 并发互斥）
  → backup_db（发布前 DB 备份，失败即中止；保留最近 15 份）
  → switch_to（写 /etc/schema-release.env + 切 current 软链 + systemctl restart）
  → verify_release：
      ① 就绪探针 UP（/internal/health/readiness，最长等 120s）
      ② 三入口 200（/、/designer/、/admin/）
      ③ 探针 commit == 目标版本
  → 任一失败：自动回滚上一版本 + 回滚后二次验证；回滚仍失败则 die 要求人工介入
  → 全过：写 release-state.json（原子写），发布成功
```

### 3.3 手工发布（救援通道，日常禁用）

```bash
ssh deploy@111.231.57.177
sudo -n bash /opt/schema/schema-release.sh status                # 先看现状
sudo -n bash /opt/schema/schema-release.sh upload <commit>       # tar 流从 stdin 进
sudo -n bash /opt/schema/schema-release.sh switch <commit>
```

### 3.4 发布记录

- 服务器侧：`schema-release.sh` 全程日志（时间戳）+ `release-state.json`；
- CI 侧：GitHub Actions `deploy` 工作流 Summary（版本/触发人/时间）；
- 本地侧：`deploy.py` 控制台输出（构建/上传/验证逐步）。

## 4. 回滚流程

### 4.1 命令

```bash
sudo -n bash /opt/schema/schema-release.sh rollback            # 回滚到 release-state.json 的 previous
sudo -n bash /opt/schema/schema-release.sh rollback <version>  # 回滚到指定版本
```

### 4.2 迁移边界闸（跨迁移回滚的保护）

- 判定：目标版本 `dbBaseline` < 当前库实际 Flyway 水位（`flyway_schema_history` 最高成功版本，`::int` 聚合）→ **拒绝回滚**（旧代码跑不动新 schema：新增列/表不可见，行为未定义）；
- ⚠️ 排坑：`max(split_part(version,'.',1))` 是 text 字典序（`'9' > '14'`），必须 `::int` 后再聚合——已修复并验证；
- 确需跨迁移回退：人工评估新旧 schema 兼容性后手动操作（`--force-db-risk` 提示语为人工救援指引，当前版本脚本未实装该参数，见 §8 缺口 G-02）。

### 4.3 回滚后的验证与记录

- `rollback` 与 `switch` 共用 `verify_release`（探针 + 三入口 + commit 一致），验证失败 die 转人工；
- 成功后 `release-state.json` 更新（current/previous 互换）。

### 4.4 迁移失败处置

- Flyway 迁移在应用启动时执行；迁移失败 → Spring Boot 启动失败 → 就绪探针不 UP → `switch` 的 `verify_release` 判失败 → **自动回滚上一版本**；
- 禁止半迁移状态上线（与测试文档 TC-UP-04 口径一致）；
- 迁移失败留下的 `flyway_schema_history` 失败记录处置：人工确认后删除失败行再重试发布（此操作在 DB 层，脚本不自动做）。

## 4a. 探针规范

| 项 | 定义 |
|---|---|
| 路径 | `/internal/health/readiness`（后端 18080） |
| 方法 | GET；期望 `200` + `{"status":"UP","commit":"<40 位 commit>",...}` |
| 超时 | 探针单次 curl `-m 5`；发布等待上限 `WAIT_TIMEOUT=120s`（每 3s 轮询） |
| 暴露面 | 不经 Nginx 暴露（`/internal/**` 未配置 location，走默认 `/api/` 之外的反代规则——**当前直接 404/拒绝**，仅本机 `curl 127.0.0.1:18080` 可达）；公网不可访问 readiness |
| 实现 | `DeploymentProbeFilter`（bootstrap），单测 `DeploymentProbeFilterTest` 6 用例（liveness/readiness/commit 注入） |
| 消费方 | `schema-release.sh` 发布验证；`deploy.py` 发布后复验；`status` 子命令 |

## 5. 备份与恢复

### 5.1 每日备份（`schema-backup.sh`，cron 03:30）

| 对象 | 方式 | 保留 |
|---|---|---|
| PostgreSQL `schema_prod` | `pg_dump`（MVCC 库级快照）+ gzip → `db-<stamp>.sql.gz` | 14 天 |
| 上传文件 `/opt/schema/data/files` | tar.gz → `files-<stamp>.tar.gz` | 14 天 |
| 发布前 DB 快照 | `pre-release-<stamp>.sql.gz`（switch 前自动） | 最近 15 份 |

- 权限：备份目录 700、备份文件 600（root/postgres）；
- 一致性：DB 与文件备份时间窗差异由文件服务「上传先落盘后写记录」顺序兜底（附件引用完整性），极端窗口靠恢复演练核对；
- 告警：失败 POST `SCHEMA_ALERT_WEBHOOK`（IM webhook，取自 `/etc/schema-platform.env` 或 `/etc/schema-release.env`）；**未配置则仅日志**——接入真实告警通道是 M16 门禁项，当前未配置（缺口 G-06）。

### 5.2 每日自动恢复演练（`restore-verify.sh`）

```
gzip -t 完整性校验
  → 恢复到独立临时库 schema_restore_test（ON_ERROR_STOP=1，失败即演练失败）
  → 核对：public 表数量 > 10；核心业务表行数（sys_user/sys_role/sys_dept/meta_model/page_schema/app/flyway_schema_history）
  → 迁移水位核对（恢复库 flyway 最高版本 > 0，防备份截断）
  → 文件备份解包计数（源目录 vs 备份 tar 内文件数）
  → 临时库清理
```

- 排坑：空 tar + `pipefail` 时 `grep -cv` 返回 1 炸管道——已 `|| true` 收口；
- **当前演练深度与 PRD 11 G3 验收线的差距**（如实登记，缺口 G-05）：
  - 未做备份前后的业务数据逐字段抽样比对（PRD 11 §3 G3：≥99.9% 抽样一致率）；
  - 未恢复应用连通性冒烟（恢复环境跑 TC-E2E-01 子集）；
  - 文件核对是「数量级」不是「逐文件哈希」；
  - 未覆盖配置层（第三层）备份。
- G3 级演练（含上述四项）按 PRD 11 §3 由 M16 收口出具 `EV-M16-DR-*` 证据物，本脚本是其脚本化基座。

### 5.3 手工恢复（整机恢复路径，人工操作）

```bash
# 1) 恢复 DB（先建空库再灌入）
runuser -u postgres -- psql -c "CREATE DATABASE schema_prod;"
zcat /opt/schema/backups/db-<stamp>.sql.gz | runuser -u postgres -- psql -d schema_prod -v ON_ERROR_STOP=1
# 2) 恢复文件
mkdir -p /opt/schema/data && tar -xzf /opt/schema/backups/files-<stamp>.tar.gz -C /opt/schema/data
# 3) 应用层直接用版本目录（releases 不依赖备份）+ systemctl restart schema-platform
# 4) 验证：探针 UP + 三入口 200（同 verify_release 口径）
```

### 5.4 RPO/RTO 口径

| 指标 | 当前口径 | 目标（PRD 11 §5） |
|---|---|---|
| RPO | 每日备份（03:30）+ 每次发布前快照 → 最坏 **24h** 数据窗口 | L-Pilot 期实测确认 |
| RTO | 单机手工恢复（§5.3），未实测 | ≤ 4h |

## 6. HTTPS 预留（当前暂缓，用户决策 2026-11-03）

### 6.1 当前限制

- 仅 IP + HTTP（80）：登录 Cookie `Secure` 属性不生效（后端按 `X-Forwarded-Proto` 判定，HTTP 下不收紧）——**登录态在公网明文传输**，上线真实用户前必须补 TLS；
- HTTPS 暂缓期间，预览/嵌入凭证与正式 Cookie 会话的安全语义按 03BE §4 口径降级评估。

### 6.2 启用检查表（域名就绪后执行）

```
[ ] DNS A 记录指向服务器；证书签发（建议 Let's Encrypt / 云厂商免费证书）
[ ] Nginx 追加 443 server 块（标识位：配置内 HTTPS-RESERVED 注释）
[ ] /api/ 反代追加 proxy_set_header X-Forwarded-Proto https
[ ] 后端 trusted-proxy 判定生效 → SessionCookies 自动收紧 Secure 属性
[ ] 80 → 443 重定向（可选：保留 80 做 ACME 续期）
[ ] 验证：Set-Cookie 含 Secure；https 三入口 200；探针 commit 不变
[ ] 更新 deploy.py SERVER / DNS 相关配置引用
```

## 7. 故障排查手册

| 症状 | 排查步骤 | 处置 |
|---|---|---|
| 上传中断/半入库 | `ls /opt/schema/staging/` 残留临时目录 | staging 未 mv 即不入库，删除残留即可；版本目录完整性由 MANIFEST 保证 |
| MANIFEST 校验失败 | 上传日志 `MANIFEST 校验失败` | 传输损坏，重新发布；检查网络/磁盘 |
| 切换后服务起不来 | `journalctl -u schema-platform -n 100`；`systemctl status schema-platform` | 自动回滚已触发则确认回滚版本探针；常见：迁移失败（§4.4）、端口占用、配置缺失 |
| 三入口 403/404 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1{/,/designer/,/admin/}` | 403 查 Nginx location 与目录权限（web 全局可读 644）；404 查 current 软链指向与 try_files |
| 探针 commit 与目标不一致 | `schema-release.sh status`；`cat /etc/schema-release.env` | env 文件未写入或重启未生效；对照 `readlink /opt/schema/current` |
| 发布锁被占 | `fuser /run/lock/schema-release.lock` | 确认无发布进行中后清锁；flock 随进程退出自动释放，正常不残留 |
| 备份失败 | `/var/log/schema-backup.log` + `backups/*.err` | 磁盘满最常见（`df -h /opt`）；失败会告警（若 webhook 已配）；连续失败视同 P0（10BE §4） |
| 恢复演练失败 | 演练日志（备份脚本内嵌输出） | 备份可能不可用——立即手工 `restore-verify.sh` 复现并排查；期间暂停发布 |
| 数据库连不上 | `systemctl status postgresql`；`ss -ltn | grep 5432` | 单机依赖，PG 挂=全站挂；`systemctl start postgresql` 后确认探针恢复 |

## 8. 实现缺口登记（如实，2026-11-03 二轮审查）

> 以下为已知未闭合项，**不因本文档存在而视为已完成**；修复后在此销项。

| 编号 | 缺口 | 影响 | 计划 |
|---|---|---|---|
| G-01 | `switch_to` 用 `ln -sfn` 直接替换软链——非严格原子（极小窗口软链可能处于替换中间态）；应改临时软链 + `mv -T` rename | 发布切换窗口内请求可能短暂 404 | 近期脚本小改 |
| G-02 | 自动回滚路径（switch 失败分支）未应用与手动 `rollback` 相同的迁移边界闸（回滚目标 `dbBaseline` 与库水位比对） | 极端场景：新版本迁移已把库推高，自动回滚旧版本违反迁移边界 | 近期脚本小改 |
| G-03 | `switch_to` 内 `systemctl restart` 直接失败（非超时）时，`set -e` 会跳过自动回滚直接退出 | 启动命令本身失败时无自动回滚，需人工 `rollback` | 近期脚本小改 |
| G-04 | 发布验证未校验页面引用的静态资源（JS/CSS chunk）实际可加载——只验入口 HTML 200 | 前端产物缺 chunk 时发布仍判成功，用户白屏 | 近期脚本小改（入口 HTML 抽 chunk URL 探测） |
| G-05 | 恢复演练深度不足 G3 验收线：无备份前后数据逐字段抽样比对、无恢复环境应用冒烟、文件核对非逐文件哈希、无配置层备份 | 不能据此宣称「备份可恢复」，G3 门禁未达 | M16 收口（PRD 11 §3） |
| G-06 | 告警 webhook（`SCHEMA_ALERT_WEBHOOK`）未配置真实通道；GitHub production 环境审批人未配置（Secrets 属用户侧操作） | 备份失败靠人看日志；CI 发布审批门空置 | 用户侧配置；M16 验证触达 |
| G-07 | 异机备份副本未落地（当前备份与数据同盘同机） | 单机盘损=备份同失，RPO 形同虚设 | 待执行：异机 scp/rsync 或对象存储 |
| G-08 | 告警触达值班演练、完整失败注入演练（TC-FT 系列）未执行 | PRD 11 G4 未验 | M16 门禁 |
