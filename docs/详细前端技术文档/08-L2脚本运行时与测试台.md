## 1. 职责边界

| 负责 | 不负责 |
|---|---|
| L2 脚本的运行时执行（钩子调度/超时/兜底） | 脚本编译（设计器保存时提交 build-service，后端文档 04） |
| 受控 ctx 的构造与冻结 | API 鉴权（ctx.api.call 走网关，服务端拦） |
| 执行日志采集与上报（logger 通道） | 脚本编辑器 UI（Monaco，测试台内嵌） |
| 测试台：mock ctx 执行 + 结果展示 | 执行日志中心存储（后端日志服务） |

**铁律：脚本报错不能导致页面白屏；红线靠代码强制不靠文档。**

## 2. 钩子契约（PRD §7.2 全量）

```ts
type HookName = 'onLoad' | 'onFieldChange' | 'beforeSubmit'
              | 'afterSubmit' | 'onActionClick' | 'onBeforeDelete';

interface ScriptBinding {
  scriptId: string;
  hook: HookName;
  artifactHash: string;        // 编译产物 hash（同轨道 B 加载约定）
  sourceHash: string;          // 源码 hash（审计"哪版源码"）
}
```

- 脚本保存流程：Monaco 编辑 → 前端**实时静态扫描**（§3 第一道闸）→ 提交 build-service 编译（第二道闸）→ 产物 hash 回写 PageSchema.scripts；
- 编译失败：测试台展示错误详情，`artifactHash` 不更新（线上继续跑旧版——与轨道 B 同兜底策略）。

## 3. 红线强制（三道闸）

```
第一道：编辑期（Monaco linter 插件，实时标红）——开发者体验层
第二道：保存提交前（前端 AST 扫描，与后端扫描器同规则文件 redlines.json）——深度防御层
第三道：运行期（Worker 隔离 + terminate 硬中断，§4）——真正的安全边界

三道闸定位修正（2026-10-28）：旧版把「module scope 无全局注入」当第三道闸——实质是
代码约定不是环境隔离，绕过成本极低。修正后第一二道拦截误用与明显恶意代码（缩小审计面），
第三道由执行环境兜底：Worker 无 DOM 环境 + 消息桥白名单 + terminate 硬中断。

⚠️ 隔离边界如实声明（2026-10-28 二次修正）：Worker 解决的是 **DOM 隔离 + 死循环硬中断 +
token 不进执行环境**三项；**普通 Worker 并不天然禁用 fetch/WebSocket/定时器/同源存储**——
Worker 线程内 `fetch`/`XMLHttpRequest`/`WebSocket`/`indexedDB` 等 API 依然可用。因此：
  · 网络出口隔离依赖 CSP `connect-src`（Worker 遵循所属文档 CSP）+ 网关侧鉴权兜底，
    不能假设「Worker 里写 fetch 会报错」；
  · 「环境断言」测试项必须断言的是 DOM/window/document 不可达 + token 不进 Worker，
    对 fetch 只能断言「红线扫描拦截 + CSP 兜底」，而非环境缺失；
  · 若后续要求出口级硬隔离（禁止一切客户脚本自发网络请求），升级为独立源 Service Worker
    代理或独立源 iframe 方案（P2 完整版评估），当前 P1 以「扫描 + CSP + 网关鉴权」三层兜底。

redlines.json（唯一真源，前端 linter / 后端 build-service 共用，CI diff 校验）：
  禁标识符：window, document, localStorage, sessionStorage, fetch, XMLHttpRequest,
           navigator, globalThis, process, require, eval, Function, importScript
  禁语法：动态 import()、with、赋值全局
  禁依赖：白名单外的 npm import（仅平台 SDK + 白名单库）
```

## 4. ScriptHost 执行器（安全模型修正 2026-10-28）

> **⚠️ 执行隔离铁律（安全评审修正）**：旧版设计假设「ESM module scope + Object.freeze(ctx)」可隔离客户脚本——**该假设不成立**：普通 ESM 模块运行在主线程全局环境，`window`/`document`/`fetch` 均可达（静态扫描只是提高攻击成本，绕过手法如原型链访问、间接引用层出不穷）；`Object.freeze(ctx)` 也拦不住脚本通过全局对象拿数据。**隔离必须由执行环境提供，不能由代码约定提供。**

### 4.1 双轨隔离架构

```
纯计算型脚本（onFieldChange/beforeSubmit 等钩子，绝大多数）：
  → Web Worker 执行（同源 dedicated worker，MessageChannel 通信）
  → 主线程仅暴露受控消息桥：{ op: 'ctx.get'|'ctx.set'|'api.call'|'log', ... }
  → ctx.form/api/ui 的每个方法 = 一次 postMessage 往返（异步化，钩子天然 async）
  → 超时硬中断：worker.terminate() —— 同步死循环可被真正终止（Promise.race/AbortSignal
    只能放弃等待结果，无法停止 worker 内的执行循环——这是旧版设计的实质缺陷）
  → Worker 内无 DOM API（window/document 为 undefined）——DOM 层环境级隔离；
    ⚠️ fetch/WebSocket 在 Worker 内仍可用，网络出口隔离靠 CSP connect-src + 网关鉴权（§3 修正声明）

UI 交互型脚本（需操作 DOM 的自定义组件逻辑，P2 完整版评估）：
  → 独立源 iframe（sandbox 最小权限集：无 allow-same-origin/allow-top-navigation）
  → postMessage 校验 origin + source + 消息 schema（zod）+ 动作白名单
  → 不与平台共享 Cookie/storage/可信接口权限；宿主代理全部 API 调用
  → 与 CSP `frame-src` 联动白名单（§CSP 策略）
```

### 4.2 受控消息桥（替代旧版冻结 ctx）

```ts
// Worker 内注入的 ctx 代理：每个方法都是 postMessage 往返，无本地能力
function createWorkerCtx(port: MessagePort): ScriptContext {
  const call = (op: string, args: unknown[]) =>
    new Promise((resolve, reject) => {
      const id = crypto.randomUUID();
      port.postMessage({ id, op, args });                    // 仅白名单 op（下表）
      port.addEventListener('message', function h(e) {
        if (e.data.id !== id) return;
        port.removeEventListener('message', h);
        e.data.ok ? resolve(e.data.result) : reject(new Error(e.data.err));
      });
    });
  return { form: { get, set, getValues, setValues },        // → op 'form.*'
          api: { call: (n, p) => call('api.call', [n, p]) }, // → op 'api.call'
          ui: { toast, confirm, dialog },                    // → op 'ui.*'（confirm/dialog 经确认弹窗代理）
          logger: scopedLogger(port),                         // → op 'log'
          user: undefined /* 由 mount 时作为静态快照注入 */,
          page: { params, query, mode } /* 同静态快照 */ };
}

// 主线程 op 白名单（桥的唯一合法指令集；新增 op = 安全评审 + 本表登记）
// form.get/form.set/form.getValues/form.setValues/api.call/ui.toast/ui.confirm/ui.dialog/log
// ⚠️ api.call 注册名先经主线程权限校验（继承当前用户 perms）再转发网关——Worker 不持 token
```

### 4.3 执行流程与超时

```
run(hook, payload):
  const script = bindings.get(hook); if (!script) return { ok: true, skipped: true };
  const worker = workerPool.acquire(script.artifactHash);   # 每页面实例独立 worker（池上限 8，LRU 释放）
  const mod = await importInWorker(worker, script.artifactHash);
  try {
    return await withTimeout(                                  # 主线程计时器
      mod[hook](payload, ctxProxy),
      { warnMs: 500, hardMs: 10_000 }                          # warn：日志告警
    );                                                         # hard：worker.terminate() 真终止
  } catch (e) {
    logger.error({ hook, err: e, scriptVersion: script.sourceHash });
    return { ok: false };                                      # 页面继续（不白屏）
  } finally {
    if (terminated) workerPool.recycle(worker);                # 终止后重建（复用池位）
  }
```

- 钩子调度点不变：挂载完成 → `onLoad`；formStore.set → 节流 50ms `onFieldChange(fieldKey, value)`；ActionDispatcher 前后 → `beforeSubmit`/`afterSubmit`；按钮动作 → `onActionClick(actionKey)`；删除确认前 → `onBeforeDelete(record)`；
- `beforeSubmit` 返回 `false` → 阻断提交；异步等待上限即 hardMs，超时按「不阻断」处理（宁可放行不卡死表单——与「脚本报错不白屏」同一韧性原则）；
- 页面卸载 dispose：池回收 + 进行中调用放弃（worker 归还前 terminate 防僵尸）。

### 4.4 三道闸修正后的定位

```
第一道（编辑期 Monaco linter）：开发者体验——实时标红，不是安全边界
第二道（保存期 AST 扫描 redlines.json）：深度防御——拦截绝大多数误用
第三道（运行期 Worker 隔离）：真正的安全边界——即使扫描被绕过，
        脚本也拿不到 DOM/token/跨域 fetch（环境不给）
```

- Worker 方案下 DOM 类 API（window/document）天然缺失；**fetch/XHR/WebSocket 并非环境缺失**——靠红线扫描拦截 + CSP `connect-src` 白名单兜底（Worker 继承所属文档 CSP）；红线扫描仍保留（拒绝明显的恶意/误用代码 + 缩小审计面）；

## 5. 受控 ctx（Worker 消息桥版，替代旧版冻结对象）

```ts
// 旧版 Object.freeze(ctx) 方案废弃（2026-10-28 安全评审）：
//   freeze 只锁对象自身，锁不住原型链与全局对象——隔离改由 Worker 环境提供（§4）
// 静态快照注入：user/page 上下文在 worker 启动时一次性传入（不随钩子变化）
user: pick(user, ['id', 'roles', 'dept']),   // 脱敏白名单（无手机号邮箱）
page: { params: page.params, query: page.query, mode: page.mode },
// 动态操作全部走消息桥（§4.2 op 白名单）：form.* / api.call / ui.* / log
```

- Worker 内无 `window`/`document`（DOM 环境缺失而非代码约束）；红线扫描仍拦截显式引用（提示开发者代码在运行环境必然失败）；**`fetch` 等 API 在 Worker 内存在**——网络隔离靠 CSP `connect-src` + 网关鉴权（§3 修正声明），不宣称环境缺失；
- `ctx.api.call` 不接受 URL，仅注册名；注册名 → 接口映射在**主线程**执行并先做权限校验（继承当前用户 perms）再走网关——Worker 不持有 token，凭证永不进入执行环境；
- 不提供定时器：防递归死循环；确需延迟用平台受管 `schedule`（P2 评估）。

## 7. 执行日志面板

- 按 hook 分组，最近 N 次真实执行（默认 50）：耗时/异常/`logger` 输出轮转；
- 客户自助排障入口（应用工作台 → 页面 → 脚本日志）；日志直传后端日志中心（`scopedLogger` 通道）；
- 渗透率指标：含脚本的页面占比（北极星过程指标，应随平台成熟下降——详细 PRD 10 §6）纳入埋点（§10 文档 usage-tracker）。

## 8. 单元测试硬性要求

- [ ] 红线三道闸：含 `fetch`/`document`/动态 `import()`/白名单外依赖的脚本在编辑期与保存期均被拒
- [ ] **Worker 环境隔离**：脚本内访问 `window`/`document` 得到 undefined（环境断言，非扫描断言）；尝试通过原型链/间接引用获取全局对象不可达
- [ ] **网络出口兜底三层**：① 红线扫描拦截显式 `fetch`/`XMLHttpRequest`/`WebSocket`；② CSP `connect-src` 白名单外的网络请求被浏览器阻断（E2E 验证，不假设 Worker 环境缺失）；③ 网关对无凭证请求 401（即使前两层被绕过，数据仍不可达）
- [ ] **超时真终止**：脚本内 `while(true){}` 同步死循环，10s 后 `worker.terminate()` 生效、主线程恢复、页面其余功能完好（旧版 AbortSignal 方案做不到——这是本次修正的核心验收项）
- [ ] **token 不进 Worker**：消息桥全量断言 `api.call` 由主线程代理，Worker 消息流中无凭证字段
- [ ] 抛错不白屏：钩子异常后页面其余功能完好且日志可查
- [ ] `beforeSubmit` 返回 false 阻断动作链；`onFieldChange` 50ms 节流合并
- [ ] 静态快照注入：`user` 字段集恰为白名单；`ctx` 方法调用均产生合法 op 消息（白名单外 op 被主线程拒收）
- [ ] dispose：卸载后 worker terminate + 池回收；产物缓存随页面释放
- [ ] 测试台保真：同一脚本在测试台（Worker + mock 桥）与真实页面执行结果一致（集成用例）

- 测试台 mock 的仅是消息桥另一端的数据源（form/user/params/api 响应），Worker 执行器、消息桥与红线扫描器为同一实例（保真承诺 §6）；

- 编译失败 `SECURITY_BLOCKED` 时测试台展示规则标识（redlines.json 条目名），`artifactHash` 不更新——线上旧版兜底。
