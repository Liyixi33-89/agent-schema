## 1. ER 建模器（data-model-designer）

### 1.1 职责

- 表节点 + 关系连线的可视化编辑（React Flow 自定义节点）；
- 字段编辑侧边抽屉（复用 schema-form 驱动）；
- **Schema Diff 预览 + 影响面确认交互**（保存前强制环节——详细 PRD 01）。

### 1.2 画布架构

```
React Flow 图：
  节点 = 模型（自定义 ModelNode：标题栏 + 字段列表虚拟滚动 + 折叠态）
  边   = meta_relation（1:1 实线 / 1:n 燕尾 / n:n 菱形中转节点）

布局：自动布局用 dagre（分层布局，关系交叉最少化）；用户手动拖动位置存 localStorage 草稿
  （布局坐标不入 Schema——坐标是视图态，非业务语义）

字段编辑：抽屉内 schema-form（FieldSchema 编辑表单——同样是"低代码编辑低代码"）：
  类型切换受限：field_key/field_type 创建后不可改（后端元数据服务铁律，前端禁用态呈现）
```

### 1.3 两段式保存（对接后端文档 01 §4.2）

```
保存流程：
  ① 前端构建 changes（与后端 op 协议一致：ADD_FIELD/MODIFY_FIELD/DELETE_FIELD/PROMOTE_COLUMN）
  ② POST /precheck → 返回 risks[] + maxSeverity + confirmMode
  ③ Diff 预览弹层（左：变更清单树；右：影响面列表按 severity 排序）
  ④ confirmMode 分级交互：
       INFO      → 一键「确认保存」
       CHECKBOX  → 勾选「我已了解影响」（每条 HIGH 风险独立勾选）
       TYPE_MODEL_NAME → 输入模型名原文（confirmValue 字段回传，服务端等值比对）
  ⑤ POST /schema { changes, baseVersion, confirmToken, confirmValue? }
     （confirmMode=TYPE_MODEL_NAME 时 confirmValue 必填；CHECKBOX/INFO 不传）
  ⑥ 409 冲突 → 三方对比（§04 §7 同款交互）；422 CONFIRM_TOKEN_INVALID（比对失败/token 过期/
     changes 篡改）→ 回 ② 重新 precheck；成功 → 画布刷新 + 版本时间线更新

前端铁律：confirmToken 一次性消费——失败后重新 precheck，禁止缓存 token 复用
删除字段二次防线：changes 含 DELETE_FIELD 时，即使 precheck 返回低风险也强制走 CHECKBOX
  （后端返回什么不重要，删除类操作前端永远高规格确认）
```

### 1.4 版本时间线与回滚交互

- 时间线抽屉：版本号/diff 摘要/操作人/时间（含 `rollback_from` 标记）；
- 回滚 = 选历史版本 → 前端展示「当前 vs 目标」字段差异 → 走**独立回滚 precheck**（`POST /rollback/precheck {targetVersion}` → confirmMode/confirmToken）→ `POST /rollback {targetVersion, confirmToken, confirmValue?}`（后端 01BE §A.3；confirmMode=TYPE_MODEL_NAME 时同样回传模型名原文）。

## 2. 流程设计器（flow-designer）

> Phase 2 全量交付（分期见文档头部声明）；P1 仅画布只读展示已有流程定义（无编辑/发布入口）。

### 2.1 节点类型系统

```
自定义 React Flow 节点（每种节点 = propsSchema 驱动的属性面板）：
  StartNode（唯一，不可删）
  ApproverNode    # 审批人配置：角色/部门/上级/字段值表达式（动态解析在后端 TaskListener）
  ConditionNode   # 条件分支：L1 表达式（与页面联动同一 ExprEngine 实例——双端语义一致）
  ParallelGateway # 并行网关
  ActionNode      # 动作：CALL_API / WRITE_DATA（走 data-engine）/ NOTIFY
  ConnectorNode   # L4 连接器动作（P2，引用已注册连接器）
  EndNode

Schema 独立于 PageSchema 但共享：表达式引擎、schema-form 属性面板、zod 校验
```

**FlowSchema 协议定义**（此前仅以节点枚举+映射表隐式存在，Schema 核心数据协议评审稿 §6.1 行动项 #3 补充的显式 TS 结构）：

```ts
interface FlowSchema {
  id: string; flowKey: string; name: string;
  appId: string; bindModelId?: string;        // 流程绑定的业务模型（动作节点读写目标）
  nodes: FlowNode[];
  edges: FlowEdge[];                          // {id, source, target, label?, conditionExpr?: ExpressionBinding}
  schemaVersion: number;                      // 迁移管线同协议层 §5，与 PageSchema 共用版本号空间
}

type FlowNode =
  | { id: string; type: 'start'; trigger: { kind: 'FORM_SUBMIT'|'CRON'; cron?: string } }
  | { id: string; type: 'approver'; assigneeRule: ApproverRule; signType: 'ANY'|'ALL' }  // 或签/会签
  | { id: string; type: 'condition'; branches: { expr: ExpressionBinding; label: string }[]; defaultBranch: string }
  | { id: string; type: 'parallelGatewaySplit' | 'parallelGatewayJoin'; pairId: string }
  | { id: string; type: 'action'; actionKind: 'CALL_API'|'WRITE_DATA'|'NOTIFY'; config: Record<string, unknown> }
  | { id: string; type: 'connector'; connectorId: string; actionKey: string; paramsMapping: Record<string, PropValue> }
  | { id: string; type: 'end'; onFinish?: { notifyInitiator: boolean } };

type ApproverRule =
  | { kind: 'ROLE'; roleId: string } | { kind: 'DEPT_HEAD' } | { kind: 'SUPERIOR'; level: number }
  | { kind: 'FIELD_VALUE'; fieldKey: string } | { kind: 'EXPR'; expr: ExpressionBinding };
```

- `FlowNode`/`FlowEdge` 与后端 Transpiler 的映射表（05BE §2.1）一一对应，本定义是该映射表的**前端可编辑结构**（服务端按此结构生成 BPMN XML）；
- `conditionExpr`/`branches[].expr` 复用页面协议同一 `ExpressionBinding`/`ExprEngine`（§1 已述"双端语义一致"）；
- 协议版本：`schemaVersion` 当前与 PageSchema 共享迁移管线实现（同一组 migration 函数按 schema 类型分派），非两套独立版本号序列。

### 2.2 保存与校验

```
前端结构校验（保存前）：
  连通性：Start→End 可达，无悬空节点/孤立分支
  网关配对：并行网关分支数 = 汇聚数；条件分支覆盖 default 路径提示
  节点配置完整性：Approver 必填审批人来源；Condition 表达式编译通过（ExprEngine）
保存：POST flow schema（后端 Transpiler → BPMN → Flowable，后端文档 05）
版本：草稿/发布态分离（与页面同模式）；发布前必须有一次模拟运行通过提示
```

### 2.3 调试能力（P1 最小集）

> P1 期间因后端 dry-run 可用但无执行实例：模拟运行提前可用（保存校验链路验证）；实例查看器随 Phase 2 流程执行闭环上线。

- **流程模拟运行**：填变量样例 → 前端按图静态推演（高亮走过的分支与解析出的审批人）——不依赖后端实例，纯前端图遍历；
- 流程实例查看器：真实实例的节点高亮 + 审批记录时间线（ApprovalTimeline 物料复用）——Phase 2 随 flow-service 上线。

## 4. 单元测试硬性要求

- [ ] 两段式保存：三种 confirmMode 交互流；confirmToken 不复用；DELETE_FIELD 永远 CHECKBOX
- [ ] 409 冲突：baseVersion 过期触发三方对比
- [ ] ER 画布：字段类型/字段名创建后禁用态；布局坐标不入 Schema 快照
- [ ] 流程校验：悬空节点/网关不配对/缺 default 分支均被阻断
- [ ] 模拟运行：给定样例变量的路径推演正确（含并行分支合并）

**对接约束**：

- 两段式保存的 `confirmMode` 三档（INFO/CHECKBOX/TYPE_MODEL_NAME）交互、`confirmValue` 回传与 confirmToken 一次性校验见 §1.3；后端 `CONFIRM_TOKEN_INVALID` 422（比对失败/过期/changes 篡改）时回到第一段重新 precheck；
- 审批人解析预览（「当前流程会找谁审批」）调 `/simulate` 的 `approvers` 结果，不单独发接口；
- 流程发布阻塞与字段引用告警共用影响面渲染组件（ER 与流程共享 risk-card）。
- [ ] 条件节点表达式与页面联动用同一 ExprEngine（同源单测回归）
