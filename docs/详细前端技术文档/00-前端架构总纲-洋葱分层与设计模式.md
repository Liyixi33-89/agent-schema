> 读法：本文是 01-11 的"地图"；任何新模块先在此对号入座，再写实现设计

## 1. 为什么是洋葱模型

低代码平台的本质是「**用代码写一个不再需要写代码的系统**」：协议（Schema）是内核，引擎围绕协议运转，应用只是引擎的宿主。这天然是洋葱结构——**越靠近中心越稳定、越抽象、越不依赖框架；越靠外越易变、越贴近具体交互**。洋葱模型的单向依赖规则正好把"稳定内核不可被外围污染"变成物理约束，而不是口头约定。

## 2. 四层洋葱模型

```
            ┌──────────────────────────────────────────────────┐
   L4 应用层 │  apps/designer · apps/runtime · apps/admin-console │  组合根 / 路由 / 组装
            ├──────────────────────────────────────────────────┤
   L3 平台层 │  request-sdk · auth-sdk · usage-tracker · shared-ui │  与"外界"打交道的一切
            ├──────────────────────────────────────────────────┤
   L2 引擎层 │  schema-renderer · schema-form · flow-designer ·   │  平台的核心业务逻辑
            │  data-model-designer · component-materials          │
            ├──────────────────────────────────────────────────┤
   L1 协议层 │  schema-protocol（类型体系 + 表达式引擎 + 迁移管线） │  纯函数、零依赖、无 React
            └──────────────────────────────────────────────────┘

依赖规则（CI 强制，文档 11 §2）：
  ① 单向：L4 → L3 → L2 → L1；禁止反向、禁止同层跨包相对路径引用
  ② L1 依赖数恒为 0（不依赖 React/浏览器 API/网络）——协议必须是可在任何 JS 环境（含 Node 测试、后端 diff 校验）运行的定义
  ③ L2 只依赖 L1 的类型与纯函数；需要"外界"（网络/存储/UI 组件）时一律通过接口反转出去（见 §4 依赖倒置）
  ④ 跨层调用必须走包公共导出（index.ts），禁止深路径 import
```

**各层职责与判据**（新代码放哪一层，按此判断）：

| 层 | 职责 | 判据：这段代码… | 落点文档 |
|---|---|---|---|
| L1 协议 | 类型、校验、表达式求值、版本迁移 | 与 React/浏览器无关、可纯函数测试 | 01 |
| L2 引擎 | 把协议"执行"起来：渲染、表单、编排、画布 | 有状态/有交互，但不知道数据从哪来 | 02/03/04/05/10/12/15 |
| L3 平台 | 网络、鉴权、埋点、通用 UI 封装 | 与外部世界（后端/浏览器能力）耦合 | 06/07/09/13/16 |
| L4 应用 | 组装一切：路由、布局、页面级状态 | 删掉它能被另一个宿主替代 | 04/06/08/14 |

## 3. 关键架构决策（洋葱视角）

| 决策 | 内容 | 违反后果 |
|---|---|---|
| 协议零依赖 | schema-protocol 不 import React | 后端契约 diff、Node 单测都要跑协议层；一旦沾框架全链路受制 |
| 引擎不碰网络 | renderer/form 只消费注入的 ctx（RenderScope/formStore/api 接口） | 引擎可在测试中脱离后端运行；换宿主（iframe/WC）不改引擎 |
| 双模式同源 | Design/Runtime 是 L2 的两个编译入口，不是两套代码 | 所见即所得是产品承诺（PRD §6.2），两套代码必然漂移 |
| 应用可替换 | runtime 容器可整体被第三方宿主嵌入（iframe/Web Component） | 嵌入是 Phase 2 需求，L4 必须薄 |

## 4. 设计模式清单（模式 → 落点 → 解决什么）

> 原则：模式只在解决已识别的问题时引入；每条都对应真实代码落点，拒绝"教科书式全家用一遍"。

### 4.1 L1 协议层

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **解释器** | ExprEngine（文档 01 §4）：Tokenizer→Parser→AST→Evaluator | L1 表达式受限求值；白名单/步数上限必须在 AST 层实现，正则过滤挡不住语义 |
| **模板方法** | migrate 管线（文档 01 §5）：固定骨架「版本检查→逐级 transform→终验」，每级迁移是可替换步骤 | 迁移链加新版本只写一个纯函数 |
| **享元** | AST 编译缓存（source→ast LRU） | 同一表达式多处求值只编译一次（性能预算 §02 §7） |

### 4.2 L2 引擎层

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **组合模式** | LayoutNode 树 + NodeRenderer 递归（文档 02 §2） | 页面结构的天然表达；容器/叶子统一处理 |
| **策略模式** | 双轨分派（文档 02 §3）：`MaterialMeta.runtime` 选 dynamic/compiled 策略 | PRD §6.2 双轨渲染的开放封闭——新增轨道不改 NodeRenderer |
| **观察者（细粒度）** | valtio 原子 store + useSnapshot 字段级订阅（文档 02 §4） | "字段 A 变化只重渲染引用 A 的节点"——性能红线 |
| **命令模式** | 设计器 Command 系统（文档 04 §3）：do/undo/label | 撤销重做 50 步栈；拖拽/大纲树/属性面板操作来源无关 |
| **中介者** | ActionDispatcher（文档 02 §2 ④）：按钮动作链（SUBMIT→TRIGGER_FLOW→CALL_API…）的编排执行 | 物料组件不互相认识，只发动作；权限拦截/幂等在中介者统一做 |
| **工厂 + 注册表** | materialRegistry（文档 05 §3）：componentName→MaterialMeta，含异步注册 | 物料分片加载、自定义物料接入对引擎透明 |
| **装饰器（HOC）** | DesignModeWrapper（文档 02 §5）：选中框/拖拽手柄包在渲染核心外层 | 设计态能力不侵入渲染核心，运行时 tree-shake 掉 |
| **观察者（reaction）** | 联动编排 buildReactions（文档 03 §3）：依赖图 + 微任务批处理 | 四种声明式联动的统一执行机制；构建期查环 |
| **桥接** | Design/Runtime 双入口（Vite define 双 entry） | 同一核心两种编译产物，物理隔离设计器代码 |
| **备忘录** | 撤销栈快照（文档 04 §3，immer 结构共享） | 快照容量可控；不做 diff patch 的复杂度权衡 |

### 4.3 L3 平台层

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **门面** | request-sdk 四层（文档 07 §2）：httpFetch→拦截器链→apiClient→hooks | 业务代码只见 hooks；租户/鉴权/trace/重试全部收口 |
| **代理** | valtio proxy 快照（只读视图给组件）；L2 脚本 ctx 的 **Worker 消息桥代理**（文档 08 §4.2——每个方法=postMessage 往返，token 不进 Worker） | 组件读状态不可变；L2 脚本拿不到本地能力，执行环境隔离 |
| **适配器** | 物料薄封装 AntD（文档 05 §5）；openapi-fetch → 类型化 client | AntD 受控契约差异抹平；手写 DTO 禁令的技术载体 |
| **单例（受控）** | AppConfig（运行时配置）；connection-manager（文档 06 §6） | 全局唯一且可测试：单例通过注入而非全局 import 获取 |
| **策略** | ThemeProvider 双通道注入（文档 13 §3）：CSS 变量 / ConfigProvider token | 品牌定制穿透 Shadow DOM（嵌入场景）与 AntD 体系双覆盖 |
| **注册表** | TaskCenter 任务类型表（文档 16 §2.4） | 异步任务 UI 单宿主：新任务只注册类型，不另建页面 |

### 4.4 L4 应用层

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **组合根** | apps 入口：装配 AppConfig + 注册物料 + 注入 ctx 实现 | 依赖注入点集中，引擎保持无环境依赖 |
| **守卫链** | 路由守卫 PageGuard → 按钮权限拦截（文档 06 §4）；admin-console 域级+页面级双层（文档 14 §6） | 菜单可见性与动作放行双层一致；平台域/租户域权限隔离 |
| **抽象工厂** | 路由表生成（应用清单→Route[]，文档 06 §2） | 应用清单驱动一切，新增页面类型不改容器 |

### 4.5 横切模式

| 模式 | 落点 | 解决什么 |
|---|---|---|
| **错误分级（错误处理策略）** | L-Schema/L-Node/L-Expr/L-Artifact 四级（文档 02 §8） | 白屏零容忍的分级兜底 |
| **纯函数变换** | responsiveTransform（文档 15 §3）：渲染管线步骤⑤，desktop 短路 | 移动适配不改 Schema 落库；设计器预览与运行时同源执行 |
| **依赖倒置（DIP）** | L2 引擎定义接口（DataSource/FormStore/ScriptContext），L3/L4 提供实现注入 | 引擎可脱离后端测试；测试台 mock ctx 与线上一致（文档 08 §6 保真承诺的技术根基） |
| **发布订阅（跨进程）** | WebSocket 发布广播 + 补拉（文档 06 §6） | 发布不发版的失效触达 |

## 5. 反模式清单（明确禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 上帝 Context（一个大 context 全树下发） | 任一字段变化全树重渲染，违反性能红线（§02 §4） |
| 引擎内直接 fetch | 破坏 DIP，测试必须起后端；换宿主即废 |
| 属性面板手写表单 | 必须由 propsSchema 自动生成（套娃复用是设计器效率根基，文档 04 §5） |
| 在 L2 保存可变全局状态 | 状态必须走 store/命令系统，否则撤销栈失效 |
| 绕过 materialRegistry 动态注册组件 | 失去分片加载与 UnknownWidget 兜底 |
| 用 JSON.parse/stringify 做深拷贝 | Date/undefined 语义丢失；immer 结构共享才是正解 |

## 6. 演进约束（洋葱各层的变化速率预期）

- **L1 最慢**（季度级变更）：协议改动必须 minor 版本 + 迁移函数 + 双端同步发版（文档 01 §5）；
- **L2 中速**（周级）：引擎迭代频繁，但公共接口（RenderScope/Command/hooks 签名）遵守语义化版本；
- **L3/L4 快速**（日级）：换 UI 库、换宿主形态不动内核——这是洋葱模型买到的最大期权。

## 7. 架构符合性验证（CI 强制，文档 11 §5 同源）

- [ ] bundle 断言：runtime 产物无设计器符号（桥接模式生效证明）；echarts 按需引入零全量（文档 12 §8）
