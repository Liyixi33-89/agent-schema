**连接池占用与分母**：应用 Hikari 池默认 max=10（无显式配置），压测全程 PG 连接稳定 17（10 应用 + 7 采样会话），**从未触及 PG max_connections=300**——瓶颈是应用 CPU 而非连接池。

**TC-FT-01 连接池占满真实性复核**（本轮新增）：注入 20 个 idle-in-transaction（占满后 PG 侧 21 active）→ 业务查询 200/0s（Hikari 池内排队不雪崩）→ 健康探针存活 → 清理后连接回落基线 11、业务正常。**结论：连接池故障注入真实占满了应用侧可用连接语义，业务确实依赖池内排队兜底。**

## 3. 250VU 未达标处置——裁决请求（二选一）

**事实**：单实例 4C/3.6G 容量基线 ≈100VU（P95<1.5s 全过）；150VU 硬 FAIL；250VU 不可达。
**选项 A（扩容复验）**：升级服务器至 8C/8G 后重跑 250VU 定档——预计需 2 轮验证（扩容窗口 + 复验），成本：服务器升配费用 + 约 1 个工作日。
**选项 B（容量调整批准）**：试点期容量目标调整为「100VU 安全水位 + 单实例限制声明」，250VU 目标保留未达标事实随多实例架构（Phase 2）重验。成本：0；试点用户并发须控制在 ~500 活跃用户以内（按 20% 并发率折算）。
**建议**：B（试点规模可控，多实例化是 250VU 达标的前置架构条件）。
