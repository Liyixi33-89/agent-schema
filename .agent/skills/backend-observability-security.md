# 后端可观测与安全纪律

## 何时使用

写任何日志/审计/指标代码，配置健康检查与告警，或处理含敏感数据的流程时。真源：`docs/详细技术文档/10-基础设施与工程规范.md` §4（可观测）、03BE §6（审计）。

## 规则/经验

1. **traceId 全链贯穿**：入网关生成/透传，响应体回带（前端工单排查依赖），日志 MDC 自动携带——**禁手写「传个 traceId 参数」层层透传**；跨服务/异步（Outbox→Kafka→消费）传播链完整。
2. **结构化日志三件**：级别语义（ERROR 需人工介入/WARN 自动恢复/BUSINESS 业务事件/INFO 常规）；JSON 结构化输出（键值可检索）；**敏感信息禁录清单**：密码/token/密钥/证件号/完整手机号（脱敏中间位）——日志泄漏是最高频安全事故源。
3. **审计事件独立通道**（03BE §6）：安全相关动作（登录/改密/越权尝试 TENANT_MISMATCH/高危确认/凭证签发吊销/恢复工单操作）写审计表非业务日志；审计记录不可修改只追加；**审计写入失败不阻断业务但必须告警**。
4. **指标埋点口径**：业务指标（流程执行数/AI token——计费依赖）从第一天埋（PRD 09 定版），计量事件走 usage 通道禁业务日志混计；技术指标（P95/错误率/连接池水位）对接可观测基座，**SLA 不可用分钟判定依赖分钟级错误率**（PRD 11 §2.1 口径——埋错口径 SLA 报表失真）。
5. **健康检查分层**：liveness（进程活着）/readiness（可接流量：DB/Redis 连通）分离；租户级健康页聚合接口（10BE §4.1）输出脱敏状态（healthy/degraded/recovering）——**禁健康接口暴露配置、版本细节、内部拓扑**。
6. **告警纪律**：告警必须可行动（附 runbook 链接，纯通知型告警清理）；P0/P1 分级路由与值班通道对齐（G4 演练对象）；阈值改动走评审（误报疲劳 = 真告警被淹）。
7. **错误上报最小化**：异常日志含异常类型 + traceId + 业务上下文（租户/资源 id），**禁整堆栈刷屏高频路径**（采样上报）；对外错误响应不含堆栈/SQL/内部路径（api-contract-error-discipline 联动）。

## 反模式（踩过的坑）

- `log.info("用户{}登录成功，token={}", user, token)` → token 进日志即泄漏；敏感字段白名单序列化器统一拦截。
- 审计写业务日志表「方便查询」 → 无不可改性无独立留存，合规审计不过关。
- 健康检查查全表 `SELECT count(*)` → 健康检查自身打死库；轻量探活 + 深检分离。
- 告警阈值「先设严点再说」 → 每天误报被全员忽略；阈值调优 + runbook 同步交付。

## 验证方式

日志审查断言：敏感字段序列化器单测（密码字段输出为 `***`）；审计事件触发用例（越权场景断言审计行落库）；健康接口响应结构断言（无配置泄露字段）；告警演练记录（TC-FT-05 归档）。
