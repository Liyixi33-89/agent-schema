# 事务与并发纪律

## 何时使用

编写事务方法、处理并发修改、实现幂等、或任何「同一数据可能被同时改」的场景。

## 规则/经验

1. **事务边界 = 单聚合**（AGENTS.md §7 后端 2）：`@Transactional` 只标 Application Service 公开方法；跨聚合一致性走领域事件 + Outbox（最终一致），**禁跨聚合同事务强一致**（锁放大 + 拆分切口丢失）。
2. **事务内禁慢操作**：RPC/HTTP/MQ 发送/文件 IO 不得在事务内——事件改走 Outbox 表同事务写入、事务后投递；事务内大循环逐条 SQL 是隐性慢操作（改批量）。
3. **并发控制选型表**：

| 场景 | 机制 | 用法 |
|---|---|---|
| 编辑保存（页面/Schema） | 乐观锁 version | WHERE 带 version，0 行更新 → 409 冲突响应（三方对比由前端裁决） |
| 席位授权/配额扣减 | 悲观行锁 | `SELECT FOR UPDATE` 串行化计数（13BE §2.4 定版：并发授权不突破上限） |
| 创建/提交防重 | 幂等键 | `Idempotency-Key` 唯一索引兜底（重复返回首次结果） |
| 状态机迁移 | 条件更新 | UPDATE ... WHERE status=当前态（CAS 语义），0 行即冲突 |

4. **隔离级别默认 READ COMMITTED**（PG 默认），不随意升级——需要串行语义的场景用行锁显式实现，禁靠 REPEATABLE READ「顺手」解决（锁范围失控）。
5. **幂等三件套**：天然幂等（PUT/删除按主键）直接做；业务幂等（创建类）唯一约束 + 幂等键表；异步消费幂等见 async-idempotency-discipline。**禁止「查一下不存在再插入」无锁防重**（check-then-act 竞态）。
6. **并发不变量必须有测试**：席位 20 路并发授权终态 ≤ 配额（02 篇 TC-SEA-02 精确断言）；并发发布同应用版本号不重；乐观锁并发提交后者 409 不覆盖（TC-DATA-02）——**只测单线程顺序路径的并发代码不算测过**。
7. **超时与回滚**：事务超时显式设置（防慢 SQL 拖垮连接池）；受检异常回滚配置确认（默认只回滚 RuntimeException——业务异常继承运行时异常统一语义）。

## 反模式（踩过的坑）

- 「加事务保险」把整个用例方法包进一个事务（内含调外部接口）→ 连接池耗尽 + 长事务锁竞争；拆边界，外部交互移出。
- 用分布式锁（Redis setnx）做本可用行锁的数据库内并发 → 多一套故障域；库内数据竞争首选库内机制。
- check-then-act 防重（先查后插）→ 并发下双插；唯一索引 + 冲突转幂等响应。
- FOR UPDATE 锁整表（WHERE 无索引）→ 全表扫描锁；确保锁谓词走索引。

## 验证方式

并发不变量测试（Testcontainers 真库多线程跑）全绿；代码审查事务方法无外部 IO；乐观锁冲突路径有集成用例（409 语义断言）。
