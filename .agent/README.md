# .agent — AI 工程化体系总览

> 本目录是「从聊天式用 AI 到工程化用 AI」的落地物。定位：把「踩过的坑、团队规范、验收口径」固化成文件，让 AI 每次都带着全员经验工作。
> 入口顺序：`AGENTS.md`（常驻）→ 本 README（体系）→ 按任务取 `specs/` 与 `skills/`。

---

## 一、AI 辅助研发完整工作流（研发生命周期 × 分工）

```text
需求分析 → 技术方案 → 编码 → 重构 → 测试 → Code Review → 问题排查
```

| 环节 | AI 用法 | 人的职责 |
|------|---------|---------|
| 需求分析 | 喂 PRD/详细PRD 提炼验收标准、边界用例、隐藏需求 | 判断业务合理性、砍范围 |
| 技术方案 | 出 2-3 个备选方案 + trade-off 对比表（对照 docs/ 已定稿架构） | 结合项目现状选型、定契约 |
| 编码 | 跨文件任务拆步骤生成、样板代码、类型补全 | 定接口、审实现 |
| 重构 | 批量改调用点、迁移 API、格式统一 | 验证语义不变 |
| 测试 | 生成单测/边界用例/测试数据 | 补 AI 想不到的业务异常 |
| CR | AI 初审（圈复杂度/命名/潜在 bug/红线扫描）预过滤 | 最终质量负责 |
| 排查 | 贴日志/堆栈归因假设、给最小复现 | 动手验证、控制成本 |

**分工原则：AI 负责宽度（快速铺开选项和样板），人负责深度（架构决策、安全边界、业务正确性兜底）。**

本项目特殊性：`docs/` 已有 33 篇评审定稿文档（PRD/技术方案/详细PRD/前后端实现级设计）。**需求分析与技术方案环节的 AI 输入不是从零生成，而是先检索既有定稿**——避免 AI 重新发明与已定稿决策冲突的方案。

## 二、上下文组织三层（核心资产）

```text
L1 项目级（长期）：AGENTS.md            技术栈/目录/权限分级/硬约束/验证管线，≤200 行常驻
L2 任务级（中期）：.agent/specs/        本次任务的需求、接口契约、验收标准（spec-kit 三件套）
L3 会话级（即时）：当前文件+依赖+报错   精准粘贴，outline → 局部读，不带无关代码
```

**AI 输出质量 = f(上下文质量)。** 三层各自防腐：L1 只写稳定规则；L2 结项即更新 status；L3 永远现场读取（实时状态禁止写进文档）。

### 2.1 Prompt 四要素（任务派发的标准写法）

1. **角色与目标**：你是本仓库的前端工程师，任务是把侧栏折叠态改为本地状态
2. **约束**：遵循 `skills/frontend-style-priority`；不改无关代码
3. **验收标准**：`verify -Level commit` 通过；刷新后默认展开
4. **输出格式**：按文件给出 diff；最后附验证步骤

反模式：一句「帮我优化这段代码」（无上下文无标准）；整仓无差别塞上下文（噪音淹没关键信息且烧 token）。

### 2.2 复杂任务编排（Agent 完整研发任务的执行链）

```text
以「跨文件重构：删除某全局状态」为例：
1. 检索：search_content 找全部引用点
2. 阅读：read_file 读 store + 消费组件上下文（outline 先行，局部读）
3. 规划：列出改动面清单（哪些文件、删什么、剩什么），必要时写进 spec
4. 执行：逐文件最小改动（replace_in_file，不顺手重构）
5. 验证：verify 三级管线 + 手动验收对照 spec 的 acceptance
```

### 2.3 上下文预算（与 AGENTS.md §5 一致）

| 内容 | 加载时机 | 预算 |
| --- | --- | --- |
| AGENTS.md | 每会话常驻 | ≤200 行 |
| 相关 spec | 按需 1-2 份 | 单份 ≤500 行 |
| 实时状态（依赖树/路由/Schema/进度） | 从代码/工具现场读取 | 禁止写进文档 |
| docs/ 设计文档 | 按任务域取对应篇 | 单次 ≤2 篇 + 精准小节 |

## 三、AI 代码审查体系

### 3.1 四个风险面

| 风险 | 典型案例（本项目高发位） | 审查手段 |
|------|---------|---------|
| 正确性幻觉 | 调用不存在的 React/zod API、编造 AntD 配置项 | 编译/测试是底线；陌生 API 查文档 |
| 安全漏洞 | SQL 拼接（data-module 动态 SQL）、XSS、密钥硬编码 | 白名单校验、secret 扫描、输入出口 review |
| 静默降级 | try-catch 吞错、隐式 any、表达式静默 undefined | lint 规则；错误分级（§02 文档四级）review 重点 |
| 规范漂移 | 违反洋葱依赖/绕过聚合根/手写 DTO | AGENTS.md 硬约束 + CI（dependency-cruiser/ArchUnit） |

### 3.2 审查清单（CR 前逐项过）

```text
□ 编译/类型检查过了吗（AI 代码不能豁免 CI）
□ 错误路径处理了吗（网络失败/空数据/权限不足/DELETED 字段）
□ 有硬编码的魔法值/密钥/路径吗
□ 遵守 AGENTS.md 硬约束吗（依赖方向/聚合根/禁 eval）
□ 有过度设计吗（AI 爱加没用的抽象层和防御代码）
□ 改动面最小吗（顺手重构是大忌，难 review）
□ 双端契约同步了吗（functions.json/redlines.json/OpenAPI/zod 任一改动）
```

### 3.3 信任校准（按代码类型分级）

```text
高信任区：样板代码、类型定义、单测生成、格式转换        直接采纳 + 编译验证
中信任区：业务逻辑、重构、配置                          逐行 review + 测试覆盖
低信任区：鉴权/加密/权限、数据迁移、破坏性操作           人写为主，AI 只做参谋
```

### 3.4 三级验证管线（执行层，写死在 AGENTS.md §8）

```text
quick   —— 文档防腐检查 + 前端 tsc + 后端 compile               每次改动后必跑
commit  —— quick + 前端 build + 后端 test                     提交前
ci      —— commit + E2E                                       联调/交付前
```

红线：失败静默重试 ≤2 次；结果自动追加 `.agent/metrics/verify-log.jsonl`。

### 3.5 CI 交付层（verify.yml 的结构性意义）

| 作用 | 说明 |
| --- | --- |
| 第三方审计 | AI 说「验证通过」是自我报告；Actions 绿勾是 GitHub 独立记录，本地不可伪造 |
| 环境差异兜底 | 本地 Windows/PowerShell，CI 是 Linux/pwsh——跨平台脚本专为这层写 |
| PR 门禁位 | 团队协作阶段把 verify 设为 required check 即升级为事前门禁 |

### 3.6 体系自身的防腐（元问题）

AI 工程体系也是文档和脚本，**它同样会腐烂，且腐烂得更隐蔽**（没人审查「审查工具」）。三条元原则：

```text
1. 检查器也要被检查 —— 防腐检查每季度人工抽查检查器本身（硬编码检查项 = 未来漏检点）
2. AI 工具是环境的一部分 —— 写回行为（丢 BOM/改行尾）是新型坑源，编辑后复查
3. 优雅降级优于误报 —— 环境结构性缺失时明确 [SKIP] 并说明由谁兜底
```

## 四、团队级落地五件套

1. **AI Rules**：AGENTS.md 硬约束条款（洋葱依赖/聚合根收口/禁 eval/禁手写 DTO）
2. **Skills 沉淀**：踩坑后固化 SKILL.md，下次同类任务自动带经验
3. **度量闭环**：AI 参与度、采纳率、返工率 → `.agent/metrics/verify-log.jsonl`
4. **工具链融入 CI**：AI 预审 PR、按 spec 验收、生成测试
5. **安全红线**：密钥不进 prompt、客户数据不外传、AI 代码等同人写代码过 CI

沉淀的制度化：回流是义务（每次返工当场更新 skill/spec）；触发信号可度量（同一背景第二次粘贴 = 固化时机）；格式对齐开源标准（Anthropic Agent Skills / spec-kit 三件套）。
